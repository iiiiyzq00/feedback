### 0.1 一分钟项目介绍

这是一个面向学习机反馈运营的多渠道分析平台。它接入通用 Android SDK、旧 Station Feedback、400 Jira、质量平台和红黑榜，在保留各来源业务口径的同时，完成加密暂存、严格脱敏、统一建模、查询看板、AI 分类、跨渠道归簇、报告、告警、权限和审计。

技术栈包括 Kotlin、Spring Boot、MySQL、Redis、Vue 3、Android SDK、Flyway，以及可选的 Elasticsearch、Milvus 和 LLM。核心设计不是“把所有数据扔给 AI”，而是：MySQL 保存权威事实；非 PASS 数据不允许进入普通查询、AI、索引、报告或导出；异步任务都有持久化状态、租约、幂等、重试和对账；ES、Milvus、LLM 和通知供应商故障不能破坏主接入链路。

## 1. 总体架构

### 1.1 五层结构

```text
接入层：SDK / Station / Jira API与文件 / 质量文件 / 红黑榜文件
    ↓
隐私层：加密暂存 → 规则脱敏 → NER → 残留扫描 → PASS或隔离
    ↓
数据层：统一来源、正文、身份、附件、渠道扩展、批次、审计
    ↓
智能层：分类、摘要、归簇、RCA、报告、告警、派生索引
    ↓
应用层：渠道页、统一查询、看板、工作台、管理与审计
```

### 1.2 为什么采用模块化单体而不是微服务

当前主要复杂度来自数据契约、隐私门禁、事务一致性和异步状态机，而不是独立团队和超大流量。模块化单体能让原子受理、幂等、权限和审计共享同一事务边界，降低分布式事务和运维复杂度。耗时或易失败能力通过数据库任务、Worker 和外部适配端口解耦。

如果未来拆分，优先拆独立伸缩、独立故障域明显的模块，例如附件扫描、AI 调用、索引同步和通知投递；统一反馈事实、权限和隐私状态不能在没有事件一致性与审计方案时随意拆开。

### 1.3 为什么 MySQL 是权威源

- 业务状态、幂等、权限、审计和对账需要强约束与事务。
- ES 适合全文检索，Milvus 适合向量召回，但都可能延迟、丢写或重建。
- 统计数字必须从权限受控的程序查询生成，不能由向量库或 LLM 猜测。
- 派生索引失败只影响搜索体验，不得把业务事务回滚成“未受理”。

标准回答：MySQL 保存事实，ES/Milvus 保存可重建视图；正向同步和删除同步都来自 MySQL，禁止派生索引反向覆盖业务数据。

## 2. 渠道模型与接入边界

### 2.1 为什么既说“五渠道”，又有四种主要来源

业务来源包括 SDK、旧 Station、Jira、质量平台、红黑榜。Station 和通用 SDK 都是实时反馈，但协议、安全、上线阶段、扩展字段、任务和指标完全不同，因此必须保留两个渠道代码：`STATION_FEEDBACK` 与 `SDK`。Jira 则有 API 和文件两个入口，但二者属于同一个 `JIRA` 渠道，共用 Issue Key 和字段映射版本。

### 2.2 统一模型为什么不等于抹平来源差异

统一主表保存跨渠道通用字段，渠道扩展表保存 Jira 状态、质量缺陷字段、红黑榜周期等专属口径。来源字段和标准字段分别保存：标准化结果可以修正和复核，但不能覆盖来源事实。

统一来源幂等边界是：

```text
source_channel + source_record_id
```

还必须保存来源事件时间、来源更新时间和接入时间，因为业务发生时间、上游修改时间和平台看见时间是三个不同概念。

## 3. 通用 Android SDK

### 3.1 完整调用链

```text
宿主初始化
→ 获取动态表单与限制
→ 生成稳定 client_feedback_id
→ 客户端基础过滤
→ AES-GCM 加密信封
→ HMAC 请求认证
→ 服务端保存 receipt并快速ACK
→ 异步解密、脱敏、正式化
→ 宿主按退避查询状态
```

### 3.2 HMAC、AES-GCM、RSA分别解决什么

- HMAC：认证应用调用方，并保护方法、路径、时间戳、nonce和正文摘要的完整性。
- AES-GCM：高效加密正文或附件，同时提供认证标签，能发现密文篡改。
- RSA-OAEP-256：封装一次性 AES 数据密钥，避免把对称密钥随请求明文传输。
- HTTPS：保护传输通道和服务端身份，但不能替代业务调用方认证、幂等或防重放。

### 3.3 防重放与幂等的区别

nonce 是一次网络请求唯一值，服务端通过 Redis 原子占位和时间窗拒绝重放；业务幂等键在同一业务重试中保持稳定，避免生成重复反馈。重试时应保持 `client_feedback_id`，更新 timestamp、nonce 和签名。

### 3.4 receipt为什么不等于处理成功

`ENCRYPTED_ACCEPTED` 只代表密文已被持久接收，不代表解密、脱敏、附件扫描、AI 或索引完成。同步接口如果等待所有步骤，会把外部依赖延迟和故障放大到用户请求线程。receipt 提供明确状态机，使“已收到”和“已完成”语义分离。

### 3.5 弱网、重试和退避

SDK在本地保存待发送任务，网络恢复后使用同一业务ID重试。400类错误通常需要修正输入；401需要校时或刷新配置；403停止重试；409查询既有状态；429遵循 `Retry-After`；网络错误和5xx使用相同幂等键做有界指数退避并加入抖动，防止惊群。

## 4. Station Feedback 兼容接入

### 4.1 业务事实

只有一个旧反馈平台，`POST /v1/feedback` 与 `POST /v1/feedback/new` 是它的 V1/V2 实时接口，共用 `FeedbackVo`，主要差异是手机号处理。当前不迁移、不拉取旧平台存量数据。

### 4.2 方案 A 与方案 B

方案 A：旧平台继续完成 UC 认证、文本审核和手机号解析，再以白名单 adapter 身份推送给新平台。优点是改动面小、能快速落地；代价是需要明确受信边界和共享密钥治理。

方案 B：新平台直接调用 UC/Dubbo，自行认证 token 和回查手机号。边界更集中，但依赖真实 RPC 包、注册中心、分组、超时和灰度配置。当前缺少目标环境契约，因此保留而未伪造完成。

### 4.3 两层身份为什么不能混淆

- 外围 HMAC 认证的是“哪个系统调用了接口”。
- UC token 认证的是“哪个终端用户提交了反馈”。

调用方ID不能替代终端用户ID，客户端正文或 Header 中的用户ID也不能直接成为认证事实。方案 A 只有白名单 adapter 签名保护后的解析结果才可被信任。

### 4.4 Station签名规范

规范串包含：HTTP 方法、原始路径、Unix秒时间戳、nonce、client ID和正文 SHA-256，各字段换行分隔，再计算 HMAC-SHA256。同一份 UTF-8 正文字节必须用于摘要、签名和发送，避免二次序列化造成字段顺序或转义差异。

重试时：业务幂等键不变，timestamp、nonce和签名重新生成。服务端必须校验HTTPS、时间窗、nonce、密钥长度和非空 `adapter-client-ids`；配置不完整时失败关闭。

### 4.5 V1/V2手机号安全

V1应以认证用户回查手机号，不信任正文 userId；V2按旧协议解密手机号，空值时回查。新平台收到后立即使用独立存储密钥加密，正文和日志不得输出手机号。旧 AES/ECB 仅为兼容输入语义，不能成为新平台静态存储方案。

### 4.6 SSRF防护为何是附件下载必需项

Station图片URL由服务端主动访问，攻击者可能借此探测内网或云元数据。下载器必须只允许HTTPS/443，拒绝凭证URL、重定向、环回、私网、链路本地、运营商NAT和组播地址，并同时防御DNS解析漂移。响应要流式限长、验证文件头、MIME和摘要，下载后仍保持隔离等待内容扫描。

## 5. Jira API与文件双入口

### 5.1 为什么保留文件入口

API改善新鲜度，文件承担历史补数、人工修复和API故障降级。两者必须写同一个 `JIRA` 渠道、复用同一个已发布字段映射版本和同一 Issue Key，不能创建两套事实或两套字段含义。

### 5.2 增量同步算法

```text
按 updated ASC, id ASC 稳定排序
从上次成功水位向前重叠一小段时间
分页安全持久化成批次
由 Issue Key + 行指纹 + source_update_time 判定新增/更新/重复/旧快照
全部分页持久化后才推进水位
```

重叠窗口解决边界时间、时钟和分页期间更新造成的漏数；幂等负责消化重复。水位必须持久化并受租约保护，不能只存在进程内存。

### 5.3 为什么先落批次再推进水位

如果先推进水位再处理，应用崩溃会永久漏数据；如果处理一页推进一次，又可能形成部分成功难以对账。先安全持久化整轮批次，再推进水位，才能用数据库事实恢复。API批次不能沿用文件的删除式回滚；纠错应按时间窗口重新读取 Jira 权威快照。

### 5.4 外部错误策略

- 401/403：认证或权限配置错误，失败关闭，不盲目重试。
- 429：遵循受控 `Retry-After`，同时设置最大等待边界。
- 网络/5xx：持久化有界退避。
- 错误记录只保存安全错误码和摘要，不能保存 Token、原始响应体或未脱敏正文。

### 5.5 ADF和人员字段

Jira Cloud 的描述可能是 ADF 树而不是普通字符串，需要受控遍历并提取文本，限制深度、节点数和最终长度。报告人、负责人等人员字段在进入批次前令牌化，避免把账号和显示名扩散到暂存、日志或映射错误报告。

## 6. Excel/CSV导入系统

### 6.1 为什么导入不是简单 `readExcel + insert`

生产导入必须处理文件边界、工作表选择、表头漂移、版本化映射、业务键幂等、旧快照、单行失败隔离、隐私、批次对账、重试和回滚。直接整表入库无法证明可复现，也容易覆盖更新数据。

### 6.2 大文件处理

- 文件、行、列、单元格长度均设置上限。
- XLSX使用 SAX/流式读取，避免DOM一次性加载导致OOM。
- 大文件使用加密分片暂存。
- 后台按固定行数切片事务，避免长事务、巨大回滚段和锁持有。
- 不同渠道公平领取任务，防止一个大批次饿死其他渠道。

### 6.3 映射版本与快照

模板定义允许表头、目标字段和必填字段。完全匹配可自动处理；未知、歧义、缺失必填或非空未映射列必须人工确认。确认后发布新版本，批次保存实际映射 JSON、枚举版本和标准化版本。历史批次继续使用自己的快照，不受后续配置漂移影响。

### 6.4 幂等和旧快照

文件 SHA-256 只能识别完全相同文件，不能替代业务键。Jira使用 Issue Key；质量平台优先问题编号，否则使用稳定组合键；红黑榜保存来源业务键和周期。相同业务键下，行指纹相同为重复，来源更新时间更早为旧快照，较新快照才更新。

### 6.5 对账恒等式

```text
新增 + 更新 + 跳过 + 失败 + 待复核 = 总行数
```

这不是展示数字，而是数据守恒约束。不成立时批次不能标记成功。失败导出只能包含行号、安全错误码和修复建议，不能把原始敏感正文重新泄漏出去。

### 6.6 回滚语义

回滚只撤销该批次产生且未被后续批次覆盖的数据变化，使用软删除或版本事实，保留批次、行级对账和审计。存在后续依赖时必须拒绝或先处理依赖，不能为了“恢复数量”物理删除治理证据。

## 7. 数据库、事务与迁移

### 7.1 当前核心数据域

- 反馈：来源、正文、身份、附件和渠道扩展。
- 导入：批次、加密暂存行、分片、Jira同步水位。
- 隐私：状态、规则版本、评测与审计。
- AI与报告：任务、调用、结果、Prompt版本、报告。
- 归簇：问题簇、当前关联、候选和人工审核。
- 告警通知：规则版本、事件、Incident、通知与回执。
- 权限审计：用户、角色、权限、数据范围和操作审计。

### 7.2 Flyway为什么禁止修改历史迁移

已执行迁移的 checksum 是数据库结构演进证据。修改历史文件会导致不同环境“同版本不同结构”，也可能诱导错误 repair。正确方式是恢复历史文件并新增前向迁移；涉及数据变换时要设计可重入、批量边界、上线时间和回滚方案。

### 7.3 为什么 Hibernate只用 `validate`

生产数据库结构必须由可审计的 Flyway 迁移控制。`ddl-auto=update` 会根据实体隐式改表，无法稳定评审、回滚或复现。`validate`只验证实体与数据库兼容，发现不一致就阻止启动。

### 7.4 唯一约束与应用幂等

应用层先查并不能防并发竞态，最终边界必须落在数据库唯一约束。应用捕获重复键后查询既有事实返回幂等结果。需要在当前事务立即捕获冲突时使用 flush，避免异常延迟到提交阶段。

### 7.5 事务应该多大

同步接入事务只包含认证后的必要校验、幂等判断、正式受理和任务种子；网络、AI、附件下载、索引和通知不进入事务。批量导入使用切片事务。原则是：事务覆盖不可分割的业务事实，不覆盖不可靠的外部等待。

## 8. 异步任务、租约与一致性

### 8.1 为什么不用只存在内存里的线程池

内存任务在应用重启后丢失，无法审计、重试或横向扩展。数据库任务表保存状态、尝试次数、下次执行时间、租约持有者、租约到期和安全错误；Worker通过原子 claim 领取。

### 8.2 租约模型

```text
PENDING/RETRY_PENDING
→ 原子claim为PROCESSING并写 lease_owner/lease_until
→ 成功COMPLETED
→ 可重试失败写 next_retry_at
→ 次数耗尽进入FAILED或DEAD_LETTER
→ PROCESSING租约过期可被恢复
```

租约比永久“处理中”锁更能应对进程崩溃。处理器必须幂等，因为租约过期、网络超时或提交结果未知都可能造成至少一次执行。

### 8.3 至少一次与恰好一次

跨数据库和外部服务很难实现真正端到端 exactly-once。项目采用至少一次投递 + 业务幂等 + 数据库唯一键 + 状态对账，达到业务效果上的“只生效一次”。声称 exactly-once 时必须说明范围，不能把消息领取一次误称为业务恰好一次。

### 8.4 调度器与Worker为什么拆开

调度器只负责定时触发，Worker负责可直接测试的领取和业务处理。拆分后集成测试可以 Mock 调度入口并确定性驱动 Worker，避免后台定时线程与测试线程争抢同一数据库任务。共享测试数据库中的断言必须按本用例唯一业务键查询，不能依赖 `LIMIT 1`、全局队首或全库为空。

### 8.5 Outbox思想

业务事务内同时写业务事实和待处理事件/任务，事务提交后由 Worker 出站。这样避免“业务提交成功但消息没发”或“消息发了业务回滚”。外部调用结果再以幂等回执更新任务状态。

## 9. 脱敏、身份与附件安全

### 9.1 多层脱敏

```text
确定性规则 → 本地NER → 高风险残留扫描 → PASS或隔离
```

手机、邮箱、证件等适合确定性规则；姓名、学校、班级和地址需要NER与上下文；高风险残留扫描负责最后失败关闭。规则版本、命中类型和处理时间可审计，普通日志不保存命中原文。

### 9.2 为什么多个出口还要再次检查

入口脱敏不能覆盖后续人工修正、旧数据、程序缺陷或字段拼装错误。因此AI、索引、查询、报告、导出和第三方调用前都执行 PASS 与字段白名单门禁，构成纵深防御。

### 9.3 联系方式存储

联系方式使用独立密钥做认证加密，并保存不可逆加盐指纹用于受控关联。加密保护可恢复数据，哈希用于等值关联；普通无盐哈希无法抵抗手机号字典枚举。展示和解密需要独立权限、理由、短时授权和审计。

### 9.4 附件四状态

- `integrity_status`：传输摘要和格式是否正确。
- `decryption_status`：是否已在可信域正确解密。
- `malware_scan_status`：ClamAV等是否明确判定清洁。
- `content_review_status`：涉黄涉暴、诈骗二维码等内容是否通过。

只有完整性验证、解密完成或无需解密、病毒扫描 CLEAN、内容审核 PASS、总状态 VERIFIED、未删除且未过期时才可查看。hash/MIME通过绝不等于病毒或内容安全通过。

### 9.5 FBA2/FBI2/FBS1

- FBA2：SDK附件，每个附件独立 AES-256-GCM key，并用RSA-OAEP-256封装。
- FBI2：导入附件采用同类独立信封契约。
- FBS1：扫描通过后，以独立存储密钥重新加密静态文件。

查看时只在受控临时流中解密，授权绑定用户、反馈、附件和理由；路径必须在配置根目录内并拒绝软链接。生产存储密钥进入 KMS/Secret Manager并支持轮换。

## 10. AI分类、Prompt与人工复核

### 10.1 AI能做什么，不能做什么

AI可以输出分类、摘要、情绪、严重度建议、风险、团队和置信度；不能直接生成统计数字、覆盖来源字段或自动成为最终高风险结论。数字由SQL/程序查询，模型只组织文字。

### 10.2 结构化输出治理

输出必须通过 JSON Schema、枚举、长度、置信度和隐私校验。未知分类失败关闭。每次调用保存 Prompt/Skill/模型版本、token、延迟、估算费用和供应商请求号，但不保存不安全原文。

### 10.3 Prompt版本发布

```text
草稿 → 结构测试 → 固定标注集评估 → 安全评估 → 双人审批 → 发布
                                                      ↓
                                               指标恶化自动/人工回滚
```

Prompt、数据集和模型都要版本化并记录哈希，否则评测无法复现。当前分类 Prompt v1.2.0 稳定准确率约74.6%，当前发布线0.74，0.85是升级目标而不是已经达到的事实。

### 10.4 严重度不是情绪

S0～S4描述单条反馈的用户影响、阻断程度、可恢复性、替代路径和安全风险。负面情绪不能自动升高等级，多人反馈不能回写单条严重度；数量和跨渠道影响由归簇与P0～P3告警处理。

- S0：安全、隐私、不可恢复数据丢失或大范围核心能力不可用。
- S1：学习完全阻断或设备完全不可用、需整机维修。
- S2：明显降级但存在替代路径。
- S3：轻微体验、咨询或建议。
- S4：纯正向且没有故障或改进诉求。

有效值优先级：人工结论 > 渠道受控值 > AI建议。S0/S1无论置信度多高都进入人工复核；低置信度结果也进入复核。

### 10.5 AI降级

LLM超时、配额耗尽、熔断或输出非法时，分类使用确定性规则，报告和助手使用SQL事实模板。降级允许功能变简单，但不能降低隐私门禁、伪造数字或把调用失败写成成功。

## 11. 跨渠道归簇

### 11.1 为什么归簇不删除来源记录

来源记录承担追溯、渠道统计和审计。问题簇是分析关系，不是物理去重。每条反馈最多有一个活跃 MAIN 关联；合并、拆分、拒绝和解除都保留历史事实。

### 11.2 候选召回与精排

候选可由结构字段、规范化错误签名、全文检索和向量召回共同产生，再综合应用、模块、版本、症状、时间、文本/向量相似度和竞争候选判断。错误签名一致是强证据，单个结构字段一致加高语义分仍不足以自动合并。

### 11.3 阈值为什么不能只拍脑袋

自动关联、人工审核和新建簇使用不同风险区间，并通过固定金标准计算 Precision、Recall、F1、错误合并率、错误拆分率、簇纯度和人工推翻率。当前归簇门禁要求 F1不低于0.75、错误合并率不高于0.05、人工推翻率不高于0.15；阈值必须通过离线集验证，不能只凭线上“看起来合理”。

### 11.4 原始反馈数与去重问题数

- 原始反馈数：权限范围内、未删除、隐私PASS的正式来源记录数。
- 去重问题数：具有活跃 MAIN 关联且未归档的问题簇数。

二者分母和业务含义不同，不能混用或相减推导“重复数”。

## 12. 告警、Incident与通知

### 12.1 三层对象

- 治理目录：规则是否具备负责人、证据、阈值来源和上线材料。
- 运行时规则版本：当前是否 ACTIVE + enabled。
- 告警/Incident实例：某次真实触发与人工处置事实。

进入目录不等于已经激活，激活规则也不等于当前存在告警。V171后治理目录期望57条，但必须带量纲说明。

### 12.2 S级与P级区别

S0～S4是单条反馈严重度；P0～P3是事件响应优先级。多条S2在跨渠道快速增长时可能形成高优先级事件，单条S0也必须高风险复核，但不能把二者当成同一枚举。

### 12.3 P0为什么不可普通静默

P0涉及安全红线或重大用户影响，普通静默会让风险从监控中消失。P0必须人工确认、转派、处理和关闭；供应商回执只证明消息送达或被确认，不代表根因已解决，更不能自动关闭 Incident。

### 12.4 通知可靠性

通知使用独立任务、幂等键、租约、重试和死信。平台记录渠道请求、供应商回执和安全错误，但不把投递失败写回业务源数据。需要监控待投递数、失败率、死信数和最老任务年龄。

### 12.5 生产上线门禁

告警规则必须具备阈值来源、回放样本、责任团队、排班、路由、供应商准入、幂等、回执、故障演练和回滚。外部安全事件源未接入时必须标记阻塞，不能创建假的成功事件。

## 13. 报告、RCA与知识库

报告数字由后端查询事实生成，AI只撰写叙述。报告任务记录主题、时间窗、数据版本和生成状态，支持取消、重试和PDF。RCA输出根因候选、证据和置信度，低于阈值必须人工审核；RCA被确认不等于问题长期解决。

知识条目区分草稿、已发布、过期和废弃；“已发布数量”不等于“当前可检索数量”。推荐采纳率应使用展示和采纳事实计算，不能把点击率包装成解决率。

## 14. 查询、看板和前端

### 14.1 权限一致性

指标卡、列表、详情、导出和报告必须使用相同数据范围与PASS条件。卡片数字能下钻时，下钻查询必须复用同一时间窗、渠道和权限，不能出现“卡片10条，列表13条”。

### 14.2 前端权限不是安全边界

Vue路由守卫和按钮权限只改善用户体验；真正授权必须由后端在API、数据范围和字段层执行。即使用户手工构造请求，后端也必须返回403并记录安全审计。

### 14.3 构建体积与缓存

HTML应 `no-store` 或短缓存，带内容哈希的JS/CSS可长期 `immutable`，这样发布新HTML即可引用新资源。分包不能只看构建成功和gzip大小，还要在全新浏览器会话验证DOM和console；错误的手工 chunk 可能形成运行时循环导致白屏。

### 14.4 SPA与API代理

Nginx需要区分静态资源、SPA fallback和 `/api` 代理。静态资源不存在应返回404而不是HTML，SPA前端路由才回退 `index.html`；敏感manifest应拒绝访问。API代理必须保留必要头并配置请求大小、超时和TLS策略。

## 15. RBAC、数据权限与审计

权限分两层：功能权限决定能否调用接口，数据权限决定能看到哪些渠道、模块、区域和字段。联系方式解密、附件查看、原文查看、导出、回滚等高风险能力使用独立权限和理由。

审计记录谁、何时、对什么对象、执行什么动作、结果如何和安全上下文。审计日志不应保存秘密或原始敏感正文。审计本身应异步持久化但不能丢失关键正式链，可通过事务内审计任务/outbox保障。

最小权限原则包括：Jira Token仅允许只读搜索；应用密钥按宿主隔离；数据库运行账号与迁移账号可分离；生产人员不默认拥有原文、联系方式或附件解密权限。

## 16. 可观测性与SRE

### 16.1 四类信号

- Metrics：吞吐、延迟、错误率、积压、租约恢复、重试和死信。
- Logs：结构化安全日志，包含request/trace/task ID，不含正文、手机号、Token或密钥。
- Traces：跨Controller、事务、Worker和外部适配器定位延迟。
- Events/Audit：业务状态变化和高风险人工操作。

### 16.2 核心SLI

- 接入成功率与P95/P99延迟。
- SDK/Station从受理到正式化的处理时延。
- 各Worker队列深度、最老任务年龄、重试率、死信数。
- 各渠道数据新鲜度。
- 隐私通过/隔离率与出站阻断数。
- AI成功率、P95、token成本、人工纠正率。
- 索引同步延迟和重建进度。
- 通知失败率、死信和供应商回执延迟。

### 16.3 为什么健康检查不能只返回进程存活

Liveness判断进程是否需要重启，Readiness判断是否可以接流量。数据库不可用通常影响readiness；外部LLM或Milvus不可用时，若系统设计有降级，不一定让核心readiness失败，但必须暴露组件状态和降级告警。

### 16.4 日志脱敏

异常日志保存错误类别、对象ID、摘要和堆栈，不保存请求体、Token、手机号或第三方原始响应。高基数字段不能随意做Metrics标签，否则会造成监控系统爆炸；业务ID更适合日志和trace。

## 17. 测试策略与证据等级

### 17.1 测试金字塔

- 单元测试：规则、签名、映射、状态机、权限判断。
- 组件测试：Spring Context、Repository、序列化和配置失败关闭。
- 集成测试：真实MySQL/Redis、Flyway、事务、Worker和HTTP链路。
- 契约测试：外部API、签名字节、错误码、分页和回执。
- E2E/真机：浏览器、Android宿主、TLS和目标供应商。
- 演练：依赖停机、超时、429、密钥轮换、回滚和恢复。

### 17.2 Mock通过能证明什么

Mock只能证明本系统对预设返回的处理逻辑，不能证明DNS、TLS、鉴权、网络、限流、真实DTO、供应商语义或性能。外部服务未配置时应标记 `BLOCKED_EXTERNAL`，而不是PASS。

### 17.3 集成测试隔离

本机集成测试只使用专用 `feedback_platform_test`，禁止清理开发库或部署库。共享CI数据库中的每个测试必须用唯一业务键限定自己的记录，并Mock会争抢任务的调度Bean，再显式驱动正式Worker。不能通过延长sleep、循环清空全局队列或反复重跑掩盖竞态。

### 17.4 覆盖率怎么看

覆盖率是回退保护，不等于正确性。全局阈值防止整体下降，变更行覆盖率防止少量新代码躲在旧覆盖中。安全状态机、权限、幂等、迁移和错误分支必须用风险驱动测试补充，不能只追求百分比。

## 18. CI/CD与仓库治理

### 18.1 分支和提交

开发在 `codex/*` 或任务分支完成，通过PR合并，不在main做常规实现提交。提交前执行静态检查，普通代码执行quick，跨栈或合并前执行full。提交必须聚焦，保留用户未提交改动。

### 18.2 门禁顺序

```text
仓库卫生/秘密扫描
→ 静态与格式
→ 后端单测和覆盖率
→ 前端测试、差异覆盖率、构建预算与npm安全审计
→ Android单测、Lint和Demo构建
→ Flyway/数据库契约
→ 跨栈集成测试
→ 制品与部署验证
```

不得使用 `continue-on-error`、删测试、降低阈值或条件跳过把红灯包装成通过。

### 18.3 为什么依赖和构建产物不进Git

`node_modules`、Gradle缓存、虚拟环境、coverage、target/build/dist、数据库备份和运行日志不可复现或体积巨大，还可能包含机器路径和秘密。仓库只保存源码、锁文件、迁移、生成器和manifest；APK/PDF/PPT等分发制品放Release或制品库。

### 18.4 SQL为什么不能用Git LFS

Flyway运行时必须直接读取文本。LFS指针在未拉取对象的环境只是三行占位，会导致迁移失败或错误校验。源码型SQL必须为普通Git文本，大型备份不进入源码仓库。

## 19. 生产部署

### 19.1 环境分层

开发、测试、预发布、生产使用独立数据库、Redis、密钥、域名、对象存储和外部应用身份。不同环境、不同用途、不同SDK宿主不得复用密钥。配置示例可提交，真实值通过KMS、Secret Manager或受控配置中心注入。

### 19.2 发布前清单

1. 代码已合并目标分支，完整CI绿色。
2. Flyway dry-run/校验通过，历史迁移未改，备份与恢复演练有效。
3. 新配置有默认安全值，缺失时失败关闭或明确降级。
4. 生产密钥已创建、授权、轮换和审计，仓库/日志无秘密。
5. 容量、连接池、线程池、队列、文件和请求上限已按压测设置。
6. 外部DNS、TLS、白名单、配额、超时、重试和回执真实验证。
7. 告警、值班、Runbook和供应商联系人有效。
8. 灰度、观测窗口、停止条件和回滚责任人明确。
9. 数据对账、隐私反向检索和权限矩阵通过。
10. 产物可追溯到提交、依赖锁、构建记录和迁移版本。

### 19.3 数据库上线

迁移评审关注DDL锁表、索引构建、默认值回填、批量更新、长事务和复制延迟。大表变更应拆分为兼容扩展、双读/双写或后台回填、切换、清理几个阶段。回滚代码时必须确认旧版本能否兼容已经前向迁移的schema；数据库通常不能依赖简单down migration。

### 19.4 灰度发布

先在小比例调用方或实例启用，观察错误率、P95/P99、积压、数据库连接、锁等待、隐私隔离率和业务对账。Station adapter还应按client ID/app白名单和比例灰度，保留旧Base URL回滚开关。

### 19.5 回滚

回滚分为应用、配置、流量、数据和外部依赖五类：

- 应用：切回上一可部署制品。
- 配置：关闭新功能开关、恢复旧路由或旧Prompt版本。
- 流量：网关切回旧Base URL或降低灰度比例。
- 数据：使用补偿、软删除或重新同步，不随意手改权威表。
- 外部依赖：打开规则/SQL降级，暂停非核心Worker。

回滚触发条件必须量化，例如签名失败率、5xx、P99、积压年龄、对账差异或隐私异常超过阈值。

## 20. 容量与性能

### 20.1 性能预算

同步接入只做有界校验和原子受理，避免调用AI、下载附件或等待索引。数据库连接池大小要结合实例数、MySQL最大连接数和查询时延，不是越大越好。外部客户端分别设置连接、读取、总请求超时和连接池上限。

### 20.2 背压

当下游变慢时，通过队列上限、领取批次、并发度、限流和熔断保护数据库与线程池。积压可接受但必须可观测；无限制并发重试会把局部故障放大成全系统雪崩。

### 20.3 缓存

Redis适合nonce、短时授权和可重建运行辅助数据，不保存唯一业务事实。缓存需要TTL、key命名、容量和穿透/击穿策略。权限和隐私状态不能因缓存故障默认放行。

## 21. 备份、恢复与灾难演练

MySQL备份必须同时验证可恢复性，而不是只验证文件生成。恢复后核对Flyway版本、44表契约、唯一键、批次守恒、Jira水位、任务租约和关键行数。Redis辅助数据可重建，但nonce窗口丢失时要评估重放风险；ES/Milvus从MySQL PASS数据重建。

演练应覆盖：MySQL只读/不可用、Redis不可用、外部API超时/429、LLM异常输出、ES/Milvus停机、ClamAV停机、通知供应商失败、密钥轮换和应用处理中崩溃。每次演练要记录检测、影响、降级、恢复和数据对账结果。

## 22. 高频“拷打题”与标准回答

### 22.1 为什么不用Kafka

当前规模和团队条件下，数据库任务表能用同一事务保证业务事实与任务种子原子提交，运维更简单，并能满足现有吞吐。它不是永远优于Kafka：当事件吞吐、消费者数量、跨系统订阅和保留回放明显增长时，可引入消息系统，但仍需要outbox、幂等和消费状态，Kafka本身不会自动提供端到端exactly-once。

### 22.2 Redis挂了怎么办

Redis用于nonce和运行辅助状态。安全认证依赖nonce时必须失败关闭，不能跳过防重放；普通MySQL查询可继续。系统暴露readiness/组件状态和告警，恢复后重新建立短期状态。不能把业务权威数据只存在Redis。

### 22.3 ES或Milvus不一致怎么办

以MySQL为准，记录同步任务状态和版本；失败可重试或全量重建。查询结果需要标识降级或改走MySQL能力。禁止把ES/Milvus结果反向覆盖MySQL，统计也不依赖它们。

### 22.4 如何证明没有敏感数据泄漏

使用带唯一敏感标记的合成输入，分别反向检索普通查询、日志、审计、导出、报告、AI调用快照、ES和Milvus；断言非PASS记录没有创建出站任务，并验证高权限原文查看具有理由、短时授权和审计。只看页面或只跑脱敏单测都不充分。

### 22.5 如何避免重复消费

任务至少一次执行，业务效果通过稳定幂等键、数据库唯一约束、状态条件更新和外部幂等回执只生效一次。处理未知结果时先查询既有状态，不能换业务键盲重试。

### 22.6 如何避免大事务

同步入口短事务，文件按固定行数切片，网络和AI移到事务外Worker。批次通过状态和对账保持整体可观察，不要求把五万行锁在一个事务里追求虚假的“全有或全无”。

### 22.7 为什么AI准确率不高还可以发布

当前0.74是经固定标注集校准的受控发布线，不是模型完美声明。AI是辅助能力，输出经过结构和隐私校验，低置信与S0/S1强制人工复核，人工结论优先，并有规则降级、版本回滚和持续评测。若业务要求全自动决策，则当前准确率不满足，不能偷换场景。

### 22.8 本地测试通过为什么不能说生产通过

本地测试没有覆盖目标DNS、证书、网络ACL、真实账号权限、限流、供应商回执、生产容量和故障域。正确结论是“代码/本地链路通过，目标环境联调待验”，并给出关闭条件和证据清单。

### 22.9 adapter-client-ids为什么必须非空

共享密钥只证明请求持有密钥，白名单决定哪个调用方被授权使用受信adapter语义。空白名单若默认放行会扩大信任边界，无法单独吊销和审计。配置缺失必须失败关闭。

### 22.10 为什么不能在代码里保存密钥

Git历史难以彻底删除，开发者和CI都可能读到，环境无法独立轮换。生产密钥必须通过秘密系统注入，按环境、用途和调用方隔离，记录访问审计，并支持双密钥过渡轮换。

## 23. 模块答辩检查表

每讲一个模块，都能回答以下问题才算真正掌握：

- 权威数据在哪里？
- 幂等键是什么？数据库唯一约束是什么？
- 状态机有哪些状态，崩溃后如何恢复？
- 哪些步骤在事务内，哪些在事务外？
- 超时、重试、退避、熔断和死信如何设置？
- 隐私门禁在哪些入口和出口执行？
- 权限是功能级、数据级还是字段级？
- 日志、指标、trace和审计分别记录什么？
- 单测、集成、契约、E2E和目标环境分别证明什么？
- 上线如何灰度，异常如何停止和回滚？
- 当前证据是什么，仍有哪些外部阻塞？
