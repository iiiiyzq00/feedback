## 汇报速记：每个指标一句话定义

> 先背本节即可；需要回答公式、阈值依据、数据源或例外情况时，再查后文对应模块。

### 接入、待办与处理漏斗

| 指标 | 一句话定义 |
|---|---|
| 数据新鲜度 | 当前时间减去该渠道最新正式反馈的接收时间，用来判断数据多久没有进入平台。 |
| 内容质量分 | 衡量反馈字段、映射、隐私和时间是否可用的综合分，不包含渠道新鲜度或观点真实性。 |
| SDK重试/失败 | 当前 SDK 回执中状态为 `RETRY_PENDING` 或 `FAILED` 的待补偿记录数。 |
| 脱敏待审核 | 当前正式反馈中隐私状态为 `REVIEW_NEEDED`、需要人工判断能否放行的记录数。 |
| 表格脱敏失败 | 非 SDK 导入行中处理状态为 `FAILED` 的隐私或数据异常行数。 |
| 待字段映射批次 | 当前状态为 `AWAITING_MAPPING`、尚待确认字段对应关系的导入批次数。 |
| 导入失败批次 | 当前状态为 `FAILED`、需要按批次排查或重试的导入批次数。 |
| AI分类待复核 | 隐私已通过且 AI 结果已生成，但复核状态仍为 `PENDING` 的不同反馈数。 |
| 归簇边界审核 | 存在活跃 `CANDIDATE + PENDING` 候选关系、等待人工决定主簇的不同反馈数。 |
| 正式接收 | 所选接收窗口内已经建立正式来源和内容记录且未删除的不同反馈数。 |
| 隐私安全放行 | 正式接收反馈中 `masking_status=PASS`、允许进入查询和下游处理的不同反馈数。 |
| 隐私处理异常 | 正式接收反馈中 `masking_status=FAIL`、未获准进入下游的不同反馈数。 |
| AI结果已生成 | 隐私通过且存在 `ai_processed_at` 的不同反馈数，不代表已经人工确认。 |
| 同类问题关联 | 隐私通过且存在当前有效 `MAIN` 归簇关系的不同反馈数。 |

### SDK 入口健康

| 指标 | 一句话定义 |
|---|---|
| 入口请求数 | 所选窗口内调用 SDK 正式反馈入口的全部请求尝试数，包含成功和所有失败。 |
| 同步受理成功数 | 入口请求中返回 HTTP 2xx、服务端已同步确认接收的请求数。 |
| 同步受理率 | 同步受理成功数除以入口请求数，衡量请求到同步 ACK 的成功程度。 |
| 未受理请求数 | 所有非 2xx 入口请求之和，等于限流、鉴权、参数、服务和其他错误数之和。 |
| 限流拒绝数 | 返回 HTTP 429、因应用或来源频率超过保护阈值而未受理的请求数。 |
| 鉴权失败数 | 返回 HTTP 401/403、因凭证、签名、时间戳或 Nonce 无效而未受理的请求数。 |
| 参数错误数 | 返回 HTTP 400/422、因必填字段、类型或加密协议不合法而未受理的请求数。 |
| 服务异常数 | 返回 HTTP 5xx、请求到达服务但服务端未完成同步受理的请求数。 |
| 其他入口错误数 | 除限流、鉴权、参数和服务异常外的其他非 2xx 请求数。 |
| 同步响应 P95 | 所选窗口入口请求耗时的第95百分位，表示95%的同步响应不超过该时间。 |
| 已落库回执 | 所选窗口内已经写入 `t_sdk_ingest` 的接入信封数。 |
| 处理完成率 | 状态为 `PASS/COMPLETED` 的 SDK 回执数除以窗口内全部已接收回执数。 |
| 处理中 | 状态为 `RECEIVED/PROCESSING`、已经接收但尚未完成后续处理的 SDK 回执数。 |
| 待人工检查 | 状态为 `REVIEW_NEEDED`、需要人工处理的 SDK 回执数。 |
| 活跃应用数 | 所选窗口入口事实中不同且不为 `UNKNOWN` 的应用标识数。 |
| 当前 RPS | 最近5分钟入口请求数除以300秒得到的平滑请求速率。 |
| 窗口平均 RPS | 所选窗口全部入口请求数除以完整窗口秒数得到的平均速率。 |
| 分箱峰值 RPS | 按窗口规定的分钟、小时或天分箱计算速率后取得的最大值，不是单秒峰值。 |
| SDK入口失败率告警 | 5分钟至少20次请求且非2xx比例达到5%时触发的 P1 告警。 |
| SDK限流率告警 | 5分钟至少20次请求且429比例达到5%时触发的 P2 告警。 |

### 数据质量与趋势

| 指标 | 一句话定义 |
|---|---|
| 单条反馈质量分 | 按必填40%、映射25%、隐私25%、时间10%计算单条正式反馈的数据可用性。 |
| 表格批次质量分 | 按完整、时间、枚举、三类映射、隐私、导入成功和跨渠道疑似重复加权计算一个批次的数据可用性。 |
| 渠道当前有效质量分 | 对五渠道当前有效正式数据及当前唯一隔离/失败事实计算的综合质量分；首页“内容质量”与渠道数据质量页使用同一快照。 |
| 最近1小时质量趋势 | 仅用于观察短期质量波动或告警，不作为首页存量内容质量的样本口径。 |
| 必填完整率 | 来源记录号和描述等规定必填字段均有效的记录数除以总记录数。 |
| 主键重复率 | 最近窗口内被判为 `SKIPPED_DUPLICATE` 的导入行数除以全部导入行数。 |
| 时间有效率 | 业务时间存在且处于允许范围内的记录数除以总记录数。 |
| 枚举有效率 | 受控枚举未出现映射错误的记录数除以总记录数。 |
| 应用映射率 | 成功得到应用标识的记录数除以总记录数。 |
| 模块映射率 | 成功得到功能模块的记录数除以总记录数。 |
| 版本映射率 | 成功得到应用版本的记录数除以总记录数。 |
| 隐私通过率 | 隐私状态为 PASS 的记录数除以总记录数。 |
| 导入成功率 | 成功新增或更新正式反馈的导入行数除以批次总行数。 |
| 跨渠道疑似重复率 | 与其他渠道反馈落入同一当前问题簇的记录数除以当前渠道记录数。 |
| 附件可用率 | 最终状态为 `AVAILABLE` 的附件任务数除以全部附件任务数，无附件时为空。 |
| 异常数 | 隐私非 PASS 或单条质量分低于0.8的记录数。 |
| 隔离数 | 隐私状态为 `PENDING/REVIEW_NEEDED/FAIL`、尚不能正常出站的记录数。 |
| 环比变化率 | 本期值减上期值后除以上期值，且本期与上期必须是相邻等长同口径周期。 |
| 字段覆盖率 | 当前筛选范围内具有受控有效字段值的反馈数除以反馈总数。 |
| 缺失数 | 当前筛选范围总数减去具有有效字段值的记录数。 |

### AI 分类、严重度与 RCA

| 指标 | 一句话定义 |
|---|---|
| AI置信度 | 模型对本次输出的自评把握，低于0.85或严重度为S0/S1时进入分类复核。 |
| 分类准确率 | 固定标注集上 AI 分类正确的样本数除以全部评测样本数。 |
| S1召回率 | 金标准为S1的样本中被系统正确识别为S1的比例。 |
| S0～S4反馈严重度 | 按用户影响、阻断程度、可恢复性、替代路径和安全风险划分的单条反馈影响等级。 |
| P1～P3归簇审核优先级 | 按反馈严重度、复发、热点量级和候选竞争确定的人工归簇审核顺序。 |
| AI安全拒绝数 | 因 Prompt 注入、敏感数据恢复请求或不安全输出被安全门禁拒绝的 AI 调用数。 |
| AI调用失败率 | 指定 Skill/Prompt 版本的失败调用数除以全部调用数，用于可用性监控和自动回滚。 |
| AI调用耗时 P95 | 指定 Skill/Prompt 版本调用耗时的第95百分位。 |
| AI人工纠正率 | 已审核 AI 结果中被人工修改分类或严重度的比例。 |
| RCA置信度 | 深度 RCA 对根因结论的把握度，低于0.70时明确要求人工复核。 |
| RCA确认率 | 深度 RCA 审核中被人工确认采用的数量占已完成审核数量的比例，但不等于长期解决率。 |

## 设计原则

1. 指标卡与下钻列表必须使用相同查询口径和数据权限。
2. 完成量、处理中、异常量、人工待办是不同队列，不得直接相加。
3. 漏斗各层必须有相同时间窗和主键；异常分支不能伪装成串行阶段。
4. 阈值必须可追溯至离线评估、容量测试、SLA 或历史分布。缺少证据时必须标为“临时阈值”。
5. 比率应同时提供分子、分母；样本不足时不下稳定性结论。

## 模块一：数据接入概览

当前总览版本为 dashboard-v3，漏斗版本为 record-funnel-v7。

### 渠道数据新鲜度与质量

- 数据新鲜度使用各渠道正式反馈的最新 `t_feedback_source.ingest_time`，衡量数据进入平台的接入时效，不使用业务发生时间。
- SDK 新鲜度 SLA 为 15 分钟；Jira、质量平台、红黑榜表格渠道均为 36 小时。阈值统一读取 `app.maintenance.freshness` 配置，不允许页面另设阈值。
- 卡片主质量指标“内容质量分”直接复用 `data-quality-v3` 渠道质量快照，不再按渠道分别使用单条评分平均或历史批次评分。渠道数据质量页展示同一快照的组成项、样本数、异常/隔离数和阈值状态，因此两处综合分不存在第二套计算口径。
- 当前有效样本包括未删除的正式反馈，以及 `ACTIVE`、非回滚导入批次中按“渠道 + 业务键”取最新状态后仍为 `REVIEW_NEEDED/FAILED` 的隔离事实；历史重试、被更新状态覆盖的旧快照和已回滚批次不重复计数。真正零样本时综合分和各比例返回空值，不以 95% 或 100% 代替。
- 综合分公式为：必填完整率25% + 时间有效率10% + 枚举有效率10% + 应用/模块/版本映射率平均值20% + 脱敏通过率30% + 非跨渠道疑似重复率5%。主键重复率和当前隔离数不重复进入综合分，但参与阈值判定和告警；接入成功率属于批次过程指标，不再混入渠道当前存量质量分。
- 五渠道均使用相同主公式，但字段适用性按渠道契约处理：例如 Jira 的应用/模块/版本、旧反馈平台的应用和模块不会因来源不提供不适用字段而被错误记为缺失。
- 质量计算不包含接入新鲜度。最近1小时窗口只用于短期趋势或质量下降告警；首页累计内容质量不能因为一小时内没有新增数据而显示“无样本”。
- 技术失败与数据失败仍须在表格导入详情中区分处置；渠道卡展示内容质量结果，不替代接入新鲜度或失败原因诊断。

### 反馈严重度：severity-policy-v2（用户视角，2026-08-06 修订）

> 本节为已激活的目标口径（2026-08-06 落地）：运行时由 `SeverityPolicyService` 读取配置（V168 迁移写入 `severity-policy-v2`，`is_active=1`），v1 保留为历史版本（内嵌常量 + 数据库 `is_active=0` 行，可回滚）；标注集 `data/annotation-sets/classify/classify-v1.json` 已按本节校准。

严重度表示**单条反馈对用户的影响**，不等于问题分类、情感强弱或处理优先级，也不随“同问题反馈条数”升级——多人反馈同一问题由归簇 + 告警规则（`CLUSTER_OCCURRENCE` 聚合、事件级 P0~P3）负责，不回写单条严重度。判级从家长/老师/学生视角回答“今天还能不能正常学习”，必须同时考虑影响范围、是否阻断学习、可恢复性、替代路径、安全风险和复现情况；多个等级同时满足时取最高等级，证据不足不得上调。

| 等级 | 正式定义 | 典型证据 |
|---|---|---|
| S0 致命 | 人身安全（漏电/冒烟/起火/过热/触电）、账号或隐私泄露、不可恢复的数据丢失，或大范围（全班/全校/所有用户）核心能力不可用 | 设备漏电；账号或隐私数据泄露；学习记录不可恢复；全班普遍无法使用 |
| S1 严重 | 学习被完全阻断：无法开机/卡 logo/进不了系统、上课闪退/自动关机、无法登录进课程；或硬件需送修换机（碎屏/无法充电/黑屏无显示/触屏完全失效/花屏无法显示） | 上课时应用持续闪退；设备无法开机；碎屏申请返厂 |
| S2 中等 | 明显降级但有替代路径：断网可开热点、白屏可重试恢复、内容错误、数据不同步、卡顿明显影响体验、音频/按键等可用替代方式 | WiFi 断网但热点可用；答案/解析错误；步数或时长不更新；界面排版错误 |
| S3 轻微 | 非阻断体验问题（加载慢/文案不清/按钮位置）、一般咨询、需求建议，或无故障证据的投诉 | UI 体验问题；功能建议；使用咨询；纯情绪投诉 |
| S4 无故障影响 | 纯表扬或正向反馈，不包含故障、风险或改进诉求 | 单纯认可课程或产品体验 |

负面情绪不能直接提升严重度；含有故障的正向表达不能判为 S4；单个“失败”“错误”等词只能作为证据，不能在缺少影响范围时直接判为 S0/S1。

外观类硬件问题（外壳变形、显示偏暗/发红/漏光、杂音、按键失灵但设备可继续使用）按“可继续使用但明显降级”判 S2，不因“返厂维修”动作一律上调 S1；只有完全不可用或需整机维修换机才判 S1。

严重度的有效值采用以下优先顺序：人工复核修正 > 渠道受控字段映射 > AI 严重度。Jira 等渠道已有明确优先级时保留其业务判断；渠道值为空时由 AI 补位；渠道值无法映射时进入字段变更待处理，不静默猜测。原始渠道严重度与 AI 建议同时保留，供审计和后续校准使用。

确定性规则、LLM 分类提示和人工复核界面必须使用本节同一套定义。新规则结果记录 `rule-cascade-v2` 或 `rule-fallback-v2`；v2 落地后证据记录 `SEVERITY_POLICY_V2`，落地前仍为 `SEVERITY_POLICY_V1`。历史结果保留原模型版本，不自动改写。S0/S1 仍必须进入人工复核。

### AI 分类复核：触发规则和 0.85 阈值

- 最终 AI 置信度低于 0.85 时进入人工复核。
- 严重度为 S0/S1 时，不论置信度多高都复核，因为高风险误判成本更高。
- 非 CONSULT 且规则分类置信度不低于 0.85 时可直接采用规则结果，否则尝试 LLM；最后仍由最终置信度和 S0/S1 规则决定是否复核。

置信度是模型对本次输出的自评把握，不等于经过校准的真实正确率。仓库没有提供“0.85 最优”的校准证据，因此它只能标为**临时阈值**。正式定值应在人工真值集上扫描阈值，比较自动通过率、错误率、S0/S1 召回率和人工工作量。现有提示词验收底线是整体准确率不低于 0.80、S1 召回率不低于 0.90，但这两项仍不能直接证明 0.85 是最佳分界。

人工工作台不通过放宽门禁来降低工作量，而是按原因分流：同时命中 S0/S1 与低置信度的记录最高优先，其次是所有 S0/S1，再处理单纯低置信度。工作台必须展示入队原因、置信度、判断依据和等待时间。批量操作只允许审核人逐条选择后批量“确认 AI 结果”；人工修正仍逐条填写分类、严重度和说明，并保留审计。

原“AI待复核”还加上了尚未执行或等待重试的 AI 任务。它们没有 AI 结果，不能由 AI 复核页处理，本次已移除混加。

### 归簇边界审核：触发规则和阈值

归簇不是单一相似度切线，而是结构证据、文本/向量证据和风险的组合：

- 高阈值 0.90：至少两项核心画像一致且文本证据达标，无竞争候选时可自动关联。
- 审核阈值 0.75：证据达到可审核程度，同时属于 S0/S1/安全风险或 AI 置信度低于 0.85 时进入人工审核。
- 严格中等阈值 0.95：只有一项结构锚点时，需要更高的向量或文本分数才允许自动关联。
- 竞争差值不高于 0.03：前两个无冲突候选过于接近时进入人工审核。
- 已解决问题的疑似复发需人工决定重开旧簇还是新建簇。
- 规范化错误签名完全一致且无强冲突时，可作为强于模糊语义分数的自动关联证据。
- 单项结构字段一致叠加高文本/向量相似度仍不足以自动关联；新决策不再写入 `AUTO_MEDIUM`。规范症状完全一致也必须先通过错误签名、复发、风险和竞争门禁。

这些数值有合理的风险分层逻辑，但缺少足够离线实验来证明数值最优，属于待验证配置。当前归簇验收门槛为 F1 不低于 0.75、错误合并率不高于 0.05、人工推翻率不高于 0.15。候选配置只有在固定验证集上同时满足三项门槛，才应发布为正式版本。

#### 处理优先级（cluster-review-priority-v1）

处理优先级用于安排人工审核顺序，不是另一套严重度。严重度描述单条反馈的用户/业务影响；处理优先级还综合疑似复发、热点量级和候选竞争，二者不得互换。

| 优先级 | 判定条件 | 处理时限 | 产品含义 |
|---|---|---|---|
| P1 紧急 | 严重度为 S0/S1 | 4小时 | 高风险误归簇可能延误事件响应，必须优先确认 |
| P2 较高 | 严重度为 S2；或候选包含已解决问题的疑似复发；或候选簇至少5条反馈、覆盖至少2个有效渠道，且前两候选文本分差不高于0.03 | 1个工作日 | 重要问题、复发和已形成量级的竞争热点需要较快确认，但不挤占紧急队列 |
| P3 普通 | 其他归簇边界不确定项 | 3个工作日 | 按常规队列处理 |

同一任务命中多项条件时取最高优先级；同级先按 SLA 到期时间、再按创建时间排序。跨渠道本身不会升为 P1，必须同时达到反馈量和强竞争条件才进入 P2。热点最少渠道数、最少反馈量及三档 SLA 均为动态配置；竞争差值沿用 `cluster.competition-margin`。历史已完成审核不重写，仅对活跃 `CANDIDATE + PENDING` 任务按新口径重算。

原“归簇边界审核”把真正待审候选与“AI 已处理但没有 MAIN 关联”的所有数据相加；后者可能会新建簇、仍在处理或根本没有审核候选。本次已移除混加，并限定为 CANDIDATE + PENDING。

### SDK 接入健康

- **当前指标版本：**`sdk-transport-v2`；`sdk-transport-v1` 只表示入口遥测开始累计的历史边界。
- **目的：**帮助产品和运营判断反馈是否稳定进入系统、接收后是否顺利完成处理，以及是否存在需要处置的异常。
- **当前数据源：**入口请求使用 `t_alert_occurrence` 中 `occurrence_type='SDK_REQUEST'` 的 `evaluation_time`；这是 V135 收敛后的物理事实，旧 `t_sdk_request_telemetry.occurred_at` 仅是迁移前来源表，V156 已退役。接收后处理继续使用 `t_sdk_ingest.received_at`。入口事实只记录结果元数据，不保存正文、签名、密钥或原始 IP。`sdk-transport-v2` 将入口结果固定为 SUCCESS、RATE_LIMITED、AUTH_FAILED、BAD_REQUEST、SERVER_ERROR、OTHER_ERROR 六类；失败总数必须等于后五类之和。
- **RPS 口径：**平均值=窗口请求数÷窗口秒数；当前值=最近 300 秒请求数÷300；峰值=所选窗口时间分箱速率最大值（1h 每分钟、6h/24h 每小时、7d 每天），不是单秒瞬时峰值。应用/IP 限流分别读取 `sdk.rate-limit` 与 `sdk.ip-rate-limit`，采用 60 秒固定窗口。
- **入口请求（遥测）：**所选窗口内且在 sdk-transport-v1 发布后的 `POST /api/v1/sdk/feedback` 全部请求尝试；包含2xx、4xx、429和5xx，配置拉取、附件与诊断事件不混入。它回答“客户端一共尝试上报多少次”。
- **同步受理成功：**入口请求中返回 HTTP 2xx 的数量，表示服务端已经返回同步 ACK；此后才会形成 t_sdk_ingest 回执。
- **同步受理率：**同步受理成功数 ÷ 入口请求数。它衡量客户端请求到同步 ACK 的成功程度，与回执落库后的处理完成率严格区分。
- **限流拒绝：**HTTP 429 请求数；错误码为 SDK_RATE_LIMITED，可按应用和时间下钻。
- **鉴权失败：**HTTP 401/403 请求数，归为 AUTH_FAILED。表示凭证、签名、时间戳或 Nonce 校验未通过，反馈未被同步受理；主要由 SDK 接入方排查配置与签名实现。
- **参数错误：**HTTP 400/422 请求数，归为 BAD_REQUEST。表示必填字段、字段类型或加密信封格式不符合协议，反馈未被同步受理；主要由客户端开发排查 SDK 版本与上报参数。
- **服务异常：**HTTP 5xx 请求数。
- **同步响应 P95：**所选窗口全部入口请求 duration_ms 的第 95 百分位；表示 95% 的同步请求响应耗时不超过该值，不包含后续脱敏、AI和归簇耗时。
- **已落库回执：**所选窗口内 t_sdk_ingest 记录数，表示同步受理成功后已经写入接入信封。它包含 sdk-transport-v1 发布前的历史数据，因此在过渡期可能大于“同步受理成功”。例如页面出现入口请求91、同步受理成功49、已落库回执193，含义是发布后观察到91次尝试，其中49次返回2xx；而193是完整6h窗口内的新落库总数，包含遥测发布前已落库的144条，口径并不冲突。
- **处理完成率：**ingest_status 为 PASS 或 COMPLETED 的回执数 ÷ 所选窗口已接收回执数。它描述“接收后的处理完成程度”，不能称为 SDK 上报成功率。
- **重试/失败：**ingest_status 为 RETRY_PENDING 或 FAILED 的回执数，应下钻到 SDK 接入异常工作台进行重新入队或排障。
- **处理中：**ingest_status 为 RECEIVED 或 PROCESSING 的回执数；用于识别积压，但需结合最老等待时间才能形成正式积压告警。
- **待人工检查：**ingest_status 为 REVIEW_NEEDED 的回执数。
- **活跃应用：**所选窗口入口 SDK_REQUEST 事实中，对不为 `UNKNOWN` 的 `dimension_key`（应用标识）去重；必须与页面时间窗口一致。`t_sdk_ingest` 的去重应用数另返回为 `acceptedAppCount`，表示已形成回执的应用，两者不能混称。
- **当前速率：**最近 5 分钟入口请求数 ÷ 300 秒。5 分钟窗口用于抑制单秒抵达抖动，不代表逐秒瞬时值。
- **窗口均值：**所选窗口内入口请求总数 ÷ 完整窗口秒数。分母分别为 1h=3600、6h=21600、24h=86400、7d=604800，因此没有数据的时段已自然计入 0。
- **分箱峰值：**1h 按分钟分箱后除以 60；6h/24h 按小时分箱后除以 3600；7d 按天分箱后除以 86400，取分箱 RPS 最大值。它是分箱峰值，不是单秒峰值。
- **低流量展示：**0 显示为 0；0 到 0.001 RPS 显示为 `<0.001`；0.001 到 0.1 显示三位小数。页面同时显示窗口回执总数和最后回执时间，避免把少量流量四舍五入成假 0。

#### 未受理异常指标

“未受理请求”是入口请求中所有非2xx结果的合计，满足：

```text
未接收请求 = 触发限流 + 鉴权失败 + 参数错误 + 服务异常 + 其他非2xx
```

| 指标 | 范围 | 代表什么 | 产品/运营处置 |
|---|---|---|---|
| 限流拒绝 | HTTP 429，result_type=RATE_LIMITED | 单应用或来源IP请求频率超过保护限制；反馈没有被同步受理 | 下钻确认受影响应用和时间分布；排查SDK重复提交、重试风暴，再决定修复客户端或调整限流 |
| 鉴权失败 | HTTP 401/403，result_type=AUTH_FAILED | 凭证、签名、时间戳或 Nonce 校验失败；反馈没有被同步受理 | 接入方按应用、错误码和 SDK 版本排查密钥配置及签名实现 |
| 参数错误 | HTTP 400/422，result_type=BAD_REQUEST | 必填字段、字段类型或加密信封格式不符合协议；反馈没有被同步受理 | 客户端开发按错误码和 SDK 版本排查参数与协议兼容问题 |
| 服务异常 | HTTP 5xx，SERVER_ERROR | 请求已经到达服务，但服务端未能完成同步受理 | 立即检查服务日志、数据库、Redis和依赖可用性；持续发生时按P1处理 |

异常指标为0代表所选窗口遥测中没有观察到该类结果，不代表遥测发布前也没有异常。点击异常原因进入“SDK入口请求明细”，只展示应用、状态、错误码、耗时和时间，不展示正文、签名、密钥或原始IP。

#### 未接收请求为什么不能在平台直接重试

未接收请求在入口阶段已经被拒绝。为避免保存未鉴权、格式不合法或可能含敏感信息的正文，入口遥测只记录应用、时间、HTTP 状态、结果类型、错误码和耗时，不保存请求正文、签名、密钥或原始 IP。因此平台没有可安全重放的原始反馈，不能提供“重新入队”，也没有向设备下发重试命令的控制通道。

- 网络异常、HTTP 429 和 HTTP 5xx 属于客户端自动重试类。SDK 已在本地 Room 队列保留反馈，由 WorkManager 自动重试；平台修复服务或限流问题后观察应用入口是否恢复即可。
- HTTP 401/403 和 HTTP 400/422 属于永久失败类。SDK 会标记 `PERMANENT_FAILED` 并触发 `onPermanentFailure`，不会自动补传；需由应用研发修复密钥、签名、SDK 版本或协议字段。网络异常、429 和 5xx 重试耗尽则标记 `RETRY_EXHAUSTED`，加密信封仍保留在设备 Room 中，可由宿主调用 `retryHistoricalFailures()` 显式补传。平台仍不能主动读取或重放设备正文。

入口异常页是接入质量监控与研发排障页面，不是逐条反馈运营工作台。同一应用随后出现成功请求只能说明“应用入口已恢复”，不能证明某条历史失败反馈已经补传成功。

#### 为什么移除接入预算参考线

原参考线按“活跃应用数 × 每应用分钟限额 × 70% ÷ 60”计算，但它既不是经过长期压测验证的容量线，也没有关联告警、责任人和处置动作；用户也不应因为流量接近参考线而停止反馈。聚合 RPS 还会掩盖单应用或单 IP 限流。因此该线已从接入概览移除，历史配置只保留兼容，不再作为运营指标。

#### 主动告警及阈值

| 规则 | 触发条件 | 级别 | 恢复 | 为什么这样设计 |
|---|---|---|---|---|
| SDK入口失败率异常 | 5分钟请求数≥20 且非2xx比例≥5% | P1 | 失败率低于1% | 20次最小样本避免一两个请求造成100%误报；5%代表反馈入口已明显影响用户，先作为初始运营阈值，后续按线上分位调整 |
| SDK限流拒绝率异常 | 5分钟请求数≥20 且429比例≥5% | P2 | 429比例低于1% | 限流是保护性拒绝而非服务故障，故低于总体失败告警级别；5%表示至少约1/20次反馈受阻，需要检查异常客户端或调整限流 |

两条规则每分钟评估，命中后在告警中心创建告警和 Incident，默认发送站内通知，冷却时间15分钟。告警快照保存请求数、实际比例、阈值和窗口。阈值属于**初始运营阈值**，不是容量压测结论；累计至少14天真实遥测后，应按应用分别查看正常失败率/P99，再决定是否调整。

当前仍未覆盖“单应用断流”主动告警，因为它需要不少于14天的分应用、分时段历史基线；在基线形成前用固定无流量阈值容易把夜间或低频应用误报为故障。

### 数据处理漏斗

统一时间窗为当日 00:00 至当前，受用户渠道/模块/地域权限约束，主键为正式反馈 source_id。

| 阶段 | 当前口径 | 解释与正确下钻 |
|---|---|---|
| 正式接收 | 所选接收时间窗内已建立 source + content 且未删除的正式反馈 | 下钻“接入事实台账”，展示来源记录号、业务时间、接收时间和当前隐私状态；未通过隐私门禁时不返回内容 |
| 隐私安全放行 | 正式接收中 masking_status=PASS | 下钻“安全放行结果”，只展示脱敏标题/摘要、敏感类型、质量分和处理版本；它必须是正式接收的子集，且不包含待复核、失败或处理中记录 |
| 待人工检查 | 已接收中 masking_status=REVIEW_NEEDED | 是隐私异常分支，不是 PASS 后的串行层；应去数据级隐私处理队列 |
| 隐私处理异常 | 已接收中 masking_status=FAIL | 是正式反馈的终止异常分支；SDK 回执和导入任务的失败态另使用 FAILED |
| AI结果已生成 | PASS 且存在 ai_processed_at | 表示分类结果已产出，不代表结果已通过复核；按 review_status 拆为自动采用、待复核、已复核、人工修正 |
| 同类问题关联 | PASS 且存在活跃 MAIN 关联 | 表示已建立主簇关系，不能下钻边界审核页；应去当日已关联明细 |

当前组件把异常分支画成同一条漏斗，视觉语义并不严谨。后续建议改成主链“已接收 → 隐私通过 → AI完成 → 已关联”，并在隐私节点旁展示“待检查/失败”两个分支。

### 页面数字为何看起来矛盾

- “AI结果已生成 100%”只表示所选接收批次均已产出分类结果，不表示准确率100%或全部无需复核。主链在同一窗口内进一步拆分自动采用、待复核、已复核和人工修正，四者之和等于已生成结果数。顶部待办卡显示的是当前全量复核积压，已明确标注其时间口径，不能与主链窗口百分比直接比较。
- “同类问题关联 633”是当日已有 MAIN 关联；原“归簇边界审核 1046”混合全量待审候选和没有 MAIN 的所有 AI 处理数据，时间窗与业务状态都不同。本次改为只统计真实 CANDIDATE + PENDING。
- “待人工检查=0、隐私处理异常=0”只表示当日正式反馈表没有相应状态，不代表 SDK 原始回执或导入行没有异常；原始数据可能在正式 source/content 建立前就失败，必须由接入异常指标表达。

## 模块二：质量、趋势与推荐指标

### 数据质量评分与内容质量评分

系统底层字段仍叫 `data_quality_score`，但总览卡对外统一称“内容质量分”，用于避免把接入新鲜度、服务可用性等技术质量混入内容评价。两种来源使用不同粒度，不能直接拿单条 SDK 分和单个导入批次分作横向排名。

| 场景 | 粒度与版本 | 计算式 | 分母与空值处理 |
|---|---|---|---|
| SDK/正式反馈记录 | 单条反馈，`quality-score-v1` | 必填完整度×40% + 映射质量×25% + 隐私通过×25% + 时间有效×10% | 必填完整度检查来源记录号、描述两项；每个映射错误扣 `1/6`，最多扣完；仅 `masking_status=PASS` 得隐私分；业务时间存在、年份不早于2000且不晚于当前24小时得时间分 |
| 表格导入批次 | 单批次，存储版本仍为 `quality-score-v1`，V161扩展字段 | 必填完整率×20% + 时间有效率×10% + 枚举有效率×10% + 应用/模块/版本平均映射率×20% + 隐私通过率×20% + 导入成功率×15% + `(1-跨渠道疑似重复率)`×5% | 以批次 `total_rows` 为主分母；映射率以该批次已建立的正式反馈为分母，无正式反馈时为0；隔离数为 `REVIEW_NEEDED`，附件可用率仍单列 |
| 渠道总览 | 当前权限下累计可见范围 | SDK 取正式记录分的平均；表格渠道对状态为 `COMPLETED/PARTIAL_SUCCESS/FAILED` 且 `quality_total_rows>0` 的全部批次按 `批次质量分×quality_total_rows` 加权平均 | 没有有效评分样本返回“无样本”，不展示为0；0表示确有样本且各分项均未得分；返回的展示契约版本为 `unified-data-quality-v1` |

附件可用率、主键重复率和无效率作为诊断子指标单独展示；跨渠道疑似重复率已按5%权重进入 V161 批次/渠道综合分。附件不是每条反馈必需，因此没有附件时不扣分；正确去重的 `SKIPPED_DUPLICATE` 也不会被当成导入失败。评分只说明字段、映射、隐私、时间、导入及疑似重复的可用性，不代表反馈观点真实、AI 分类正确或渠道准时。

#### V161 统一渠道质量快照：`data-quality-v2`

除总览卡的历史累计/批次加权展示外，系统每5分钟计算四渠道最近1小时的运行快照，并写入 `t_alert_occurrence`：

```text
渠道质量分 = 必填完整率×25% + 时间有效率×10% + 枚举有效率×10%
            + 应用/模块/版本平均映射率×20% + 隐私通过率×30%
            + (1-跨渠道疑似重复率)×5%
```

最近1小时没有样本时，各比例按1、质量分按1处理，但不会触发阈值告警；必须同时展示 `totalCount=0`，不能汇报成“有数据且质量100%”。快照另列异常数（非PASS或记录质量分低于0.8）、隔离数（PENDING/REVIEW_NEEDED/FAIL）和阈值状态。

当前动态阈值为：必填完整率≥95%、时间有效率≥98%、枚举有效率≥95%、应用/模块/版本各自映射率≥90%、隐私通过率≥99%、主键重复率≤5%、跨渠道疑似重复率≤30%、隔离数=0。渠道级主键重复率按最近一小时表格导入行中的 `SKIPPED_DUPLICATE / 总导入行数` 计算；没有表格导入行的 SDK 实时渠道记为 0，不把已被唯一约束拦截的请求虚构成重复样本。批次另外要求导入成功率≥90%，并按该批次重复跳过行计算主键重复率。任一项越界即 `thresholdStatus=ALERT`，创建 P2 `DATA_QUALITY_THRESHOLD_BREACH`；相同渠道或批次30分钟内去重。告警事件当前携带质量分85/90的展示阈值，但真正触发依据是上述分项门禁，汇报时不得简化成“质量分低于85就告警”。

### 环比变化

环比必须比较两个**等长、相邻、同权限、同筛选、同业务时间字段**的周期：

```text
环比变化率 =（本期值 - 上期值）÷ 上期值 × 100%
```

- 总览的“近7天”比较本期7天与紧邻的前7天；`current`、`previous` 和 `periodDays=7` 一起返回。
- 报告按用户选择的 `[periodStart, periodEnd]` 计算本期，上期为向前平移同样天数的闭区间；按渠道分别给出本期数、上期数和变化率。
- 日趋势中的“日变化率”只比较相邻自然日，不应口头汇报成周环比。
- 上期为0时变化率返回 `null/—`，不能展示“增长100%”或“无限增长”；此时直接汇报“上期0、本期N”。本期和上期都为0同样不计算。
- 数量变化不等于质量变化或风险变化；必须同时展示两个周期的绝对样本数，小样本不作稳定趋势结论。

### 推荐命中率

知识库首页的“推荐命中率”实际是**采纳率**：

```text
推荐命中率 = Σ adoption_count ÷ Σ shown_count
```

统计对象为 `t_ai_knowledge` 中所有知识条目的累计展示与采纳计数；分母为0时返回0。它回答“已展示的知识推荐有多少被用户采纳”，不是向量检索 Top-K 召回率、答案正确率或问题解决率。知识是否真正解决 Incident 由独立的知识使用/有效性事件验证，不能用点击采纳替代。汇报时建议称“知识推荐采纳率（页面字段：推荐命中率）”；后续若需要离线检索命中率，应另建带标准答案的评测集，并定义 Hit@K。

## 模块三：AI 分类、Skill 与 Prompt 治理

### 分类类别如何设定

分类字典版本为 `ai-taxonomy-v1`，采用“用户反馈的主要诉求/问题性质”单选七类；严重度 S0～S4 是另一维度，不能用类别推导严重度。

| 编码 | 含义 | 主要边界 |
|---|---|---|
| BUG | 软件功能异常、崩溃、卡死或行为与设计不符 | 硬件实体故障归 HARDWARE；题目/答案本身错误归 CONTENT_ERROR |
| HARDWARE | 设备、屏幕、电池、摄像头等物理部件问题 | 软件驱动或应用行为异常仍按 BUG |
| CONTENT_ERROR | 题目、答案、解析、课程等内容事实错误 | 单纯内容需求或新增建议归 DEMAND |
| DEMAND | 新功能、优化或产品改进诉求 | 已有功能故障归 BUG；使用方法提问归 CONSULT |
| CONSULT | 使用咨询、规则询问、求助，未表达明确故障 | 有明确异常证据时不能为了低风险而兜底为 CONSULT |
| PRAISE | 纯正向认可且无故障、投诉或改进诉求 | 含故障的正向表达按故障类别，严重度也不能为 S4 |
| COMPLAINT | 服务、体验或态度投诉，但没有更具体的 BUG/硬件/内容错误主类 | 能归入具体问题性质时优先具体类别 |

AI 待复核依据仍为：最终置信度 `<0.85`，或严重度为 S0/S1；两项同时命中时在队列最前。0.85 是临时治理阈值，S0/S1 强制复核是风险门禁。结果必须记录分类字典、Skill、Prompt、模型和规则版本；人工复核可确认或修正，优先级为人工结论 > 渠道受控值 > AI 建议。

### Skill 和 Prompt 如何设计

- **Skill 是能力契约**：定义稳定的 `skill_code`、用途、输入输出结构、允许调用范围和 Skill 版本，例如 `feedback_classify`、报告生成、分析助手和告警路由。它回答“系统要完成什么能力”。
- **Prompt 是能力的可发布实现**：每个 Skill 可有多个语义化版本；正文、模型参数、文件路径和 SHA-256 登记在 `prompts/manifest.json`，Git 是唯一内容源，数据库只是审批后的运行时投影。它回答“当前版本如何让模型完成该能力”。
- 分类 Prompt 使用温度0和 JSON 输出，写入七类分类边界、S0～S4定义、证据码和结构化字段要求，以降低随机性并使结果可校验；报告/助手 Prompt 只叙述后端已计算的事实，不允许模型自行改数。
- 发布链路为 DRAFT → 结构测试 → 脱敏真值集真实模型评测 → 不同 ADMIN 复核批准 → 小流量/影子发布 → 逐步放量。Git 内容、哈希或模型参数不一致时拒绝创建/启动；未知输出类别失败关闭。
- 每次调用快照保存 Skill/Prompt 版本与ID、SHA-256、模型配置、应用版本、token、延迟、费用和供应商请求号，保证报告可以复现。
- 当前版本15分钟内至少20次调用且失败率达到10%时自动回滚上一版；影子结果只写评测事实，不改业务字段。该回滚阈值是故障保护线，不是模型准确率门槛。

## 模块四：告警规则与等级

### 为什么这样定义规则

告警规则遵循“可观测事实 → 最小样本/时间窗 → 触发阈值 → 恢复阈值 → 责任人和动作”的闭环。阈值只允许来自四类证据：明确安全红线、业务 SLA、容量/故障实验、或足够长的历史基线；没有证据的值标为初始运营阈值。触发与恢复采用不同阈值形成滞回，冷却抑制同一故障反复建单；比例规则设置最小样本，避免1次失败就形成100%误报。规则发布前还必须通过数据契约完整性/新鲜度、历史回放、恢复、路由和通知演练，目录中“已登记”不等于“已启用”。

### 告警等级如何划分

告警 P0～P3 表示**事件处置紧急度**，与反馈严重度 S0～S4、归簇审核优先级 P1～P3分别建模：

| 告警级别 | 定义与典型场景 | 处置约束 |
|---|---|---|
| P0 | 已确认或高度可信的人身安全、隐私/账号泄露、不可恢复数据损失等红线事件 | 不允许普通静默；恢复不等于关闭；必须人工填写结论并完成安全闭环 |
| P1 | 核心链路大面积失败、入口显著不可用，或需立即响应的高影响事件 | 立即通知主责与值班，快速确认和升级；例如 SDK 5分钟至少20次且非2xx≥5% |
| P2 | 局部/可恢复降级、保护性拒绝或短期内需处理的质量风险 | 工作时限内排查；例如同样样本下429比例≥5%，因限流仍保护服务故低于总体失败 |
| P3 | 提醒、趋势异常或低影响治理待办 | 常规队列观察和处理，不应打扰高等级值班链路 |

治理目录仍保留完整业务规则历史。V163 将当前代码内置风险规则统一发布为 `risk-v1`，V165 补齐治理元数据；V169 新增 11 条用户反馈 P0 规则后期望数为 53；V171 又将 4 条 `SYSTEM_NOTIFY_*` 通知自监控规则纳入目录，当前正式治理期望数为 **57 条**。该数字表示治理目录应完整覆盖的规则代码数，不等于57条都已激活或正在产生告警。当前覆盖接入量、导入、脱敏、版本/问题簇风险、用户安全、内容安全、数据质量、AI 和通知链自监控等领域。只有活动版本、实现证据、数据契约、审批和路由门禁均满足时才允许运行。数据库、磁盘、进程等通用基础设施故障仍由 Prometheus/Alertmanager 负责，必要时通过鉴权 webhook 汇入 Incident。

#### `risk-v1` 当前关键阈值

| 规则 | 当前触发口径 | 等级/恢复 |
|---|---|---|
| 表格渠道新鲜度异常 | JIRA/QUALITY/REDBLACK 最近文件陈旧≥2880分钟 | P1；低于1440分钟恢复 |
| 导入失败率过高 | 30分钟行数≥100且失败率≥10% | P2；低于5%恢复 |
| 脱敏失败率过高 | 15分钟尝试≥20且失败率≥1% | P1；低于0.5%恢复 |
| AI/脱敏连续失败 | 分别在30/15分钟内连续失败数≥5 | P1；恢复计数为0 |
| 高风险跨渠道 | S0/S1高风险有效问题簇跨不少于2个渠道，计数≥1 | P0；归零后仍需人工闭环，不可普通静默 |
| 设备安全强证据/敏感暴露确认 | 24小时开放事件数≥1 | P0；归零后仍需人工闭环，不可普通静默 |
| 长期未解决 Jira | 24小时窗口候选数≥1 | P3；归零恢复 |

`SDK_VOLUME_ANOMALY`、版本多渠道异常、负面突增和内容错误突增使用代码计算的候选指标达到1即触发；其候选公式必须随告警事实快照一起解释，不能只汇报“阈值为1”。

## 模块五：SDK 录屏与附件

### SDK 录屏为什么默认30秒

SDK 默认配置为 H.264/MP4、24fps、约1000kbps、最长30秒；服务端配置允许1～120秒，但默认30秒是体验、可诊断性、隐私暴露面、弱网上传耗时和本地空间的折中。按默认码率，仅视频码流约 `1000kbps × 30s ÷ 8 ≈ 3.75MB`（实际文件还含封装开销），通常足以覆盖“触发问题前后”的最短复现链，又不会让用户长时间处于系统录屏状态。30秒不是模型或网络推导出的最优值，属于产品默认值；若调整，应以真实设备文件大小、用户取消率、问题复现覆盖率和弱网上传成功率验证。录屏必须由用户主动选择并通过 Android MediaProjection 系统授权，前台服务显示通知，到时硬停止，无音频采集。

### SDK 附件如何处理

1. 截图、编辑后截图、录屏和诊断日志仅在用户主动选择/提交时进入反馈；日志在反馈窗打开时冻结，只取此前3分钟的 SDK/宿主诊断事件。
2. 明文附件只在内存中存在到提交加密；每个附件派生独立密钥，使用 AES-256-GCM 加密后写入应用私有目录，主体和附件清单先落 Room。
3. 主体先上传并取得严格校验的 receipt；附件再按 `receipt + client_attachment_id` 独立续传。服务端校验ID、类型、MIME、声明大小、SHA-256及动态大小上限，先写临时文件，校验通过再原子移动并登记元数据。
4. 网络异常、429、5xx由 WorkManager 在联网条件下指数退避；附件与主体均可在进程/安装包替换后恢复，服务端以附件ID幂等。永久协议/鉴权错误不盲目重放。
5. 查看附件不暴露存储路径：有权限用户先说明访问原因，获得默认5分钟、绑定用户/反馈/附件的一次性令牌；令牌只存哈希，消费后失效并写审计。安全流未启用时生产环境失败关闭。

### 表格导入附件如何处理

- 表格只接收附件 URL 及可选 SHA-256/大小，不在普通行字段里保存或回显明文 URL。系统先校验协议、域名和附件类型，URL 随即加密保存，附件元数据创建为 `PENDING + QUARANTINED`。
- 附件是独立任务，与导入行通过 `parent_import_row_id` 和正式反馈关联；下载/上传失败不会伪装成正文导入成功。任务保存期望哈希和大小，实际密文上传必须通过 MIME 白名单、大小、声明值和 SHA-256 校验，成功后才变为 `AVAILABLE`。
- 附件可用率=`AVAILABLE附件任务数÷附件任务总数`；没有附件时为 `null` 而不是100%，且该比率不进入综合质量分。对账导出同时给出每行附件总数和可用数。
- 直接上传、分片上传、合并、附件上传及映射确认统一要求 `action:upload_file`。分片是加密冷数据，合并成功/过期后按生命周期清理；原始行密文在导入成功且过回滚窗口后销毁。

## 模块六：数据库表与跨渠道指标说明

### 为什么数据库显示42张表

最终物理库是 **41张业务表 + 1张 Flyway 元数据表 `flyway_schema_history` = 42张 BASE TABLE**。所以“原38张增加三张”指的是业务表从38张变为41张，并不是38+3=42；第42张是迁移框架维护的表，不承载业务数据。

新增并保留的三张隔离业务表为：

1. `t_authorized_contact_vault`：隔离加密联系方式及附件一次性授权令牌，避免与普通业务字段混放。
2. `t_http_audit_queue`：HTTP审计投递采用可变租约、重试队列语义，不适合并入只追加审计日志。
3. `t_import_upload_chunk`：保存导入分片的临时加密大对象，隔离冷大字段，避免拖慢热点行表并重复存储载荷。

其余后期扩展表已按领域收敛进 `t_system_config`、`t_ai_task`、`t_system_audit_log`、`t_alert_occurrence`、`t_import_batch/t_import_row` 等紧凑表。V156 最终删除47张兼容期影子表；“42张”是迁移完成后的实际物理计数，不是把历史所有建表脚本相加。

### 跨渠道关联表为什么看起来涉及很多严重度

跨渠道关联表的统计单位是**问题簇**：同一个有效 MAIN 问题簇只要包含至少两个可见渠道就入表。问题簇内可以有多条反馈，每条反馈都保留自己的 S0～S4，因此一行展开后出现多个严重度是正常的，表示同一类问题在不同用户、版本或影响范围下后果不同；系统没有因为“跨渠道”自动提高反馈严重度。

表中的“平均归簇相似度”仅对当前有效 MAIN 且有 `match_similarity` 的关联取平均，同时展示有分数样本数和完整率；它不是同一用户概率、同一事件概率、根因置信度或严重度。当前跨渠道主表聚合展示的是关联告警 `alertLevel`，而不是把簇内 S 值粗暴平均；风险简报中的“跨渠道严重问题”另有明确门槛：簇内存在 S0/S1 且渠道数不少于2。跨渠道只说明影响信号在多个来源出现，只有与 S0/S1、热点量级、竞争候选或活跃告警等证据组合后，才影响风险或审核优先级。

因此汇报时应分开说：`channelCount` 是传播/证据广度，S0～S4 是单条反馈影响，P0～P3 是告警处置等级，P1～P3 是归簇审核顺序。若页面把这些都标成“严重度”，属于展示命名问题，不能据此认为系统在一个字段里混算。

## 模块七：其他系统指标补充

### 核心业务 KPI：反馈、问题簇、渠道关联、Jira时效与活跃告警

总览当前版本为 `business-kpi-v6`。五个核心计数分别回答不同问题，不构成串行漏斗：

| 指标 | 统计单位与口径 | 不能如何解释 |
|---|---|---|
| 反馈总数 | 权限范围内、未删除且隐私通过的不同 `source_id`；同一问题的多次反馈分别计数 | 不是独立问题数，也不是全部入口请求数 |
| 去重问题数 | 上述反馈通过当前有效 `MAIN` 关系关联的不同、非合并/拆分归档问题簇数 | 不是 `反馈数-重复数`，未归簇反馈不计入 |
| 跨渠道问题数 | 当前有效 MAIN 问题簇中，包含不少于2个可见渠道的簇数 | 不是跨渠道反馈条数，也不代表同一用户 |
| 单渠道问题数 | 当前有效 MAIN 问题簇中，只包含1个可见渠道的簇数 | 不是“未归簇反馈”；一个问题簇即使有多条同渠道反馈仍只计1个 |
| 活跃告警数 | 权限范围内状态为 `FIRING` 或 `ACKNOWLEDGED` 的告警实例数 | `RESOLVED/CLOSED` 不计；一簇可有多个规则实例 |

`crossChannel + singleChannel` 只对已经有有效 MAIN 的问题簇分组；在相同权限与状态口径下应与去重问题簇集合对账，但未归簇反馈仍不进入两者。当前 `business-kpi-v6` 接口不再返回 Jira 平均解决时长、QUALITY 跨渠道数或 REDBLACK 跨渠道数；这些专题数据应从报告或问题分析接口按各自周期查询，不能继续当作总览 KPI 字段汇报。

总览主数默认是当前权限下全量现状；反馈、去重问题、跨渠道和单渠道卡片的环比固定比较近7天与前7天。点击进入分析页时必须携带 `allTime=true` 才能与全量主数对账，不能拿分析页默认近30天直接比较。V6 返回的方法说明明确为：隐私门禁仅 PASS、原始反馈按来源记录、去重按有效 MAIN、四渠道计数不做样本量加权；合并趋势只观察方向，渠道绝对量受实时上报与文件快照频率差异影响，不宜直接排名。

### 字段覆盖率与缺失治理

版本、严重度、可重现性、省份/城市都同时展示有效值分布和字段覆盖率：

```text
字段覆盖率 = 有受控有效值的反馈数 ÷ 当前筛选范围反馈总数 × 100%
缺失数 = 总数 - 有效值数
```

`NULL`、空字符串和不在受控枚举中的值统一归入 `UNKNOWN`，未知项不应从分母消失。覆盖率回答“数据是否足够完整”，不是业务表现好坏。例如严重度覆盖率100%不代表没有严重问题；地区热度只对有省份/城市值的数据排序，同时必须披露被排除的缺失数。各渠道采集能力不同，页面还按渠道给出缺失数，便于定位字段治理责任方。

### 可重现性指标

受控定义 `reproducibility-v1` 为：复现率=`同条件成功复现次数÷同条件有效尝试次数`。同条件至少要固定应用版本、设备型号、操作系统、网络、账号/数据状态和步骤，比例分类至少需要3次有效尝试：必现≥90%，频繁为50%～90%，偶发为0～50%；只观察到一次且证据不足时记“一次”，不能把1/1宣称为100%必现。

当前系统只保存来源给出的分类结果，没有保存复现实验的尝试数和成功数，因此页面不会自动计算复现率；来源明确提供受控标签时归一化，否则为 `UNKNOWN`。汇报时应说“复现标签分布及完整率”，不能说平台已经自动完成复现实验。

### 热点、突增与地区热度

- 热点问题按当前筛选范围内有效 MAIN 问题簇的关联反馈数降序；它反映反馈量，不直接代表严重度或独立用户数。
- 功能模块排行只接受统一受控枚举中的产品功能（如错题本、同步课程、网络连接）；“系统相关、应用软件、三方应用、硬件相关、重复提交”等 Jira 原始标签不是同层级功能模块，保留在渠道原始字段并计入“待确认模块”，不得直接进入 TOP8。
- 应用版本对比默认展示全渠道，也可切换单渠道；比较键必须同时包含应用身份和版本号，不得把不同应用的相同版本号合并。本期和上期均为 0 的版本不展示。Jira 应用身份仅从其脱敏标题/描述中匹配 Station 渠道已存在的权威应用名称，多名称命中时取最长名称，未命中记录暂不进入具体应用版本对比。
- 分析页的 `spike` 是本期数量比等长上期高20%以上且上期大于0，即 `current > previous×1.2`；这是页面提示线，不是正式告警，也没有最小样本门禁。
- 风险简报中的负面突增门槛是环比大于30%，按渠道和模块形成风险因子；同样必须结合绝对数量阅读。
- 地区热度全国层按省份聚合，进入省份后按城市聚合；缺失地区不参与排名但计入完整率。热度是反馈量分布，不等于用户渗透率，因为系统没有以地区活跃用户数作分母。

### 归簇算法质量指标与发布门禁

归簇在线相似度用于单次候选决策；算法版本能否保留则由独立标注集评估，二者不能混用。正式评估要求100～5000条脱敏样本、四渠道每个至少10条、预测簇/金标准簇齐全，并对每个预测簇给出人工 `GOOD/BAD`：

| 指标 | 含义 | 当前门禁 |
|---|---|---|
| Precision | 系统判为同簇的样本对中，金标准确实同簇的比例 | 与 Recall 合成 F1 |
| Recall | 金标准同簇样本对中，被系统正确合并的比例 | 与 Precision 合成 F1 |
| F1 | Precision 与 Recall 的调和平均 | ≥0.75 |
| 错误合并率 | 不同金标准问题被判成同簇的比例 | ≤0.05 |
| 人工推翻率 | 人工最终没有采用系统推荐决定的比例 | ≤0.15 |
| 簇纯度 | 各预测簇内占比最大的金标准成员合计÷已归簇成员数 | ≥0.80 |
| 错误拆分率 | 同一金标准问题被拆到多个预测簇的程度 | ≤0.15 |
| 未归簇率 | 标注样本中没有预测簇的比例 | ≤0.15 |

所有人工簇结论还必须为 GOOD。证据不全结论为“补齐”；主要为过度拆分且其他质量合格时为“合并”；混簇、人工判坏或门禁失败时为“重构”；全部通过才为“保留”。这些阈值是项目验收门禁，不等同于生产发布批准。

### 隐私处理与脱敏模型质量

业务流水中的 `PASS/REVIEW_NEEDED/FAIL/PENDING` 是每条反馈的隐私处理状态；脱敏版本发布前的算法质量则使用独立评测集：NER F1、端到端 F1、高风险召回率、误脱敏率、通过样本数/总样本数。高风险召回强调手机号、身份标识等红线实体不可漏掉，误脱敏率约束过度删除对内容可读性的损害。只有数据集、执行日志哈希、失败样本摘要和审批证据齐全且门禁通过，版本才可发布；线上 PASS 率不能替代离线高风险召回率。

### RCA 指标与人工审核

快速 RCA 是告警详情中的定位线索；深度 RCA 才进入四 Agent 审核工作台。深度 RCA 置信度低于0.70时强制标记人工复核，该阈值与分类0.85不是同一含义。RCA 证据分为事实、部分支持和假设，置信度不能把假设升级成事实。人工可确认、修正或驳回；驳回不得发布知识，确认/修正也只有审核人主动选择才沉淀知识。当前系统衡量的是审核状态、置信度和证据闭环，尚不能把“RCA已确认率”解释为根因长期解决率。

### 七类报告的主次指标

报告概览沿用 `six-report-overview-v1` 兼容契约，当前实际已有七类：在原六类基础上新增 Jira 导入与对账报告。反馈型报告的主指标按不同 `source_id` 计“有效反馈”，次指标按有效 MAIN 的不同 `cluster_id` 计“主问题簇”，另列“未归簇反馈=有效反馈中没有 MAIN 的记录数”。每日接入和每周趋势统计全渠道；Jira对账按批次、PASS记录及对账状态；版本观察增加包名+版本条件；质量关联仅 QUALITY；红黑榜仅 REDBLACK；风险简报按风险权限和周期。所有反馈型报告只统计未删除、隐私PASS且业务时间（缺失时回退接收时间）位于周期内的数据，并固化生成时的权限、事实、Prompt/Skill和模型快照；历史报告不随数据库变化回写。

### 通知投递健康指标

通知链路单独暴露以下运行指标，不能只看“告警已创建”：

- Prometheus 的 `alert.notification.pending` 兼容指标统计 `PENDING/SENT/FAILED`；其中 SENT 仍可能等待供应商最终回执。V157 闭环健康页的 `pendingNotifications` 只统计 `PENDING/FAILED`。两者名称相似但分母不同，排障时必须同时带指标来源；积压还需结合最老等待秒数。
- `failed`：当前失败任务数；`dead_letter` 是进入死信且尚未关闭的任务数；`retry_exhausted` 是重试耗尽总数。
- `failure_rate_5m`：最近5分钟投递尝试中 `FAILED÷全部尝试×100%`；没有尝试时为0。
- 投递耗时按渠道和成功/失败结果记录 Timer，可观察 P50/P95/P99；它只覆盖通知供应商调用，不等于告警从触发到人员响应的总时长。

`SENT` 只说明平台已向供应商发送，最终送达要以 provider receipt 为准；站内已读、外部送达、人工确认和 Incident 解决是四个不同阶段，不能合并成一个“通知成功率”。

### 版本上线观察与回归候选

版本观察以 `packageName + version + releasedAt` 固定范围，比较发布版当前问题簇占比与发布前7天控制版本占比。系统的回归候选要求当前30分钟同一簇至少20条、占发布版反馈至少1%，且占比达到控制版本的2倍；它是需要调查的候选，不自动证明新版本导致故障。必须继续核对灰度比例、用户规模、渠道结构和根因证据。

### 指标对账、版本与权限

- 主链提供 today、滚动24h、滚动7d三种对账，正式接收、隐私四状态、AI四状态和归簇两去向均以不同 `source_id` 计数；JOIN 扩张不得增加数量。
- 每个指标应携带 `metricVersion`、实体类型、去重键、时间字段、默认窗口、定义和下钻路径。历史快照保留旧版本，不因新口径静默重算。
- 页面卡片、导出、报告和下钻必须使用同一权限快照；channel、module、region 任一权限为空时失败关闭为0，而不是回退到全局数据。
- `generatedAt` 是指标计算时间，`dataLatestTime` 是参与数据的最新时间，`sourceEventTime` 是业务发生时间，`ingestTime` 是平台接收时间。三者回答不同问题，汇报时不得混称“数据时间”。
- 项目验收 PASS 证明口径、状态机和自动化链路可重复，不代表生产容量、正式供应商 SLA、真实业务阈值最优或上线批准；所有临时/初始阈值必须在生产样本形成后重新校准。

## 模块八：V157～V166 最新运行与安全指标

### 告警闭环健康度

V157 新增只读闭环健康接口，面向 ADMIN/AUDITOR，检查四个必须覆盖的规则域：接入失败 `DATA_INGEST`、数据质量 `DATA_QUALITY`、热点/舆情 `PRODUCT_TREND`、隐私处理 `MASKING`。每个域至少存在一个 `ACTIVE + enabled` 规则才算覆盖。

| 状态 | 判定 |
|---|---|
| NOT_READY | 四个必备规则域中至少一个没有活动规则 |
| DEGRADED | 规则域已覆盖，但存在 `DEAD_LETTER` 通知 |
| HEALTHY | 四域均覆盖且死信数为0 |

运行快照同时返回最后评估时间、开放告警数、24小时恢复数、待投递/失败通知数、死信数和最后成功发送/送达时间。该健康度证明“规则启用→评估事实→告警实例→通知/回执→恢复或关闭”的链路是否具备运行证据，不代表当前业务没有风险；例如 `HEALTHY + openAlerts>0` 表示系统健康地发现了仍待处理的风险。

### 来源更新时间与批次对账（V158～V159）

V158 将 `t_feedback_source.source_update_time` 设为必填：历史缺失值回填为 `source_event_time`，再回退 `ingest_time`。三个时间字段的最新含义为：

| 字段 | 当前用途 |
|---|---|
| `source_event_time` | 业务实际发生时间；趋势和报告优先使用，缺失时才回退接收时间 |
| `source_update_time` | 来源记录最后更新时间；增量导入判断新快照、旧快照和更新覆盖的依据，不再允许为空 |
| `ingest_time` | 平台接收/正式入库时间；接入新鲜度、漏斗和运行窗口使用 |

V159 后导入批次分别保存 `inserted_rows` 与 `updated_rows`。批次守恒应按“新增 + 更新 + 跳过 + 失败 + 待复核 = 总行数”核对；旧的 `success_rows` 是兼容汇总字段，不能继续解释为全是新增。Jira 时效、质量平台业务日期和红黑榜数据周期均保留为各渠道事实，不互相替代统一业务时间。

### 出站隐私阻断指标

V160 后，查询详情、导出、AI/报告等出站自由文本需再次通过当前脱敏版本。发现正文会被规则改写或结果不是 PASS 时：阻断响应/导出；有关联反馈则把其隐私状态改为 `REVIEW_NEEDED`；写入 `OUTBOUND_PRIVACY_REJECT` 安全审计，保存目标、规则版本、命中类型和字段数，不保存原文。

建议运营指标为“出站隐私阻断数”，按 `target + ruleVersion + findingType` 统计审计事件；它表示安全门禁实际拦截次数，不等于已经发生外泄。当前实现尚未在总览提供独立卡片，应从安全审计下钻，不能用流水中的 masking FAIL 数替代。

### AI 安全拒绝与降级

V162 后 AI 输入增加 Prompt 注入和敏感数据恢复请求拦截，输出也拒绝包含指令劫持特征的内容。对应错误为 `AI_PROMPT_INJECTION_REJECTED`、`AI_SENSITIVE_RECOVERY_REJECTED`、`AI_UNSAFE_OUTPUT_REJECTED`。这些应按 Skill、Prompt版本、入口和时间统计为“AI安全拒绝数”，与供应商失败、超时、熔断降级分开：安全拒绝是门禁生效，不应计为模型可用性故障。

AI 结果字段现已扩展为应用、功能模块、情绪、风险类型和数据来源证据；它们是 AI 派生值，必须与原渠道字段并存，详情页不得将其冒充来源事实。自然语言助手只允许基于权限范围内的脱敏事实生成叙述；降级时返回确定性 SQL 事实，不应伪造 AI 推断。

### 字段级权限覆盖

V164 在渠道、模块、地区权限之外新增 `FIELD` 范围。没有 FIELD 配置时维持原有字段可见性；一旦配置，则按 ALLOW/DENY 过滤，DENY 优先，`*` 表示全部。`ID/SOURCE_CHANNEL/STATUS/REPORTED_AT` 是维持列表可解释性的系统字段，始终保留。

字段级权限会改变页面、详情和导出的列，但不应改变同一行级权限下的计数分母。因此汇报某个覆盖率或质量分时，应说明“数值按有权记录计算；明细字段再经过FIELD裁剪”。若用户无权查看构成字段，只展示聚合结果和口径，不通过错误信息或导出旁路泄露被拒字段。

### 告警治理目录完整率（V171 当前口径）

V165 曾将正式治理规则期望数修正为42；V169 增至53，V171 纳入4条通知自监控后增至57。建议用以下两个数分别汇报，避免把“目录完整”和“运行激活”混为一谈：

```text
治理目录完整率 = 具备完整治理元数据的正式规则代码数 ÷ 57
运行激活率 = ACTIVE 且 enabled 的正式规则代码数 ÷ 当前具备运行前提的正式规则代码数
```

治理元数据至少包括规则名称、类别、默认告警等级、责任团队、评估模式、参数模板、恢复策略、数据依赖、实现证据和 P0 不可静默标识。目录完整率100%只证明57条规则均可解释、可审计，不代表全部规则的数据契约、值班人和供应商门禁都已满足，更不代表当前存在57个告警实例。

### AI 结果成为业务事实的边界（V166）

V166 明确了 AI 分类结果进入 `t_feedback_content` 规范业务字段的条件：只有 `review_status=NOT_REQUIRED`、类别属于 `ai-taxonomy-v1` 七类且严重度属于 S0～S4时，才能补齐原本为空的 `issue_category/severity_level`。该迁移使用 `COALESCE`，不会覆盖渠道已有值或人工值；`PENDING` 结果不会提前进入规范事实。

因此相关指标应按以下优先级读取：人工/来源规范字段 > 已允许采纳的 AI 规范字段 > AI 建议字段。AI“结果已生成”统计所有已产出结果，规范“分类/严重度分布”统计 `t_feedback_content` 当前事实，两者分母可能不同；待复核结果只能出现在 AI 复核队列和建议详情中，不能提前改变正式分布、热点规则或报告事实。人工 `CONFIRMED/CORRECTED` 后的规范字段由审核链路更新，不由 V166 的历史补齐逻辑替代。

### 报告生成与删除的最新边界

当前报告类型实际为7类：每日接入、Jira导入对账、每周多渠道趋势、版本观察、质量关联、红黑榜分析和风险舆情简报。风险简报仍可定时生成，但最新版本已移除“生成后自动通知投递”；报告通知记录不应计入普通告警通知成功率。

所有报告删除均为物理删除，并同步清除该报告关联的通知及投递尝试事实，再写删除审计；因此列表/报告数量是当前存在的报告数，不包含已删除历史。不可变业务审计仍保留“谁删除了哪类报告及删除模式”，但不会保留已删除报告正文或投递载荷。
