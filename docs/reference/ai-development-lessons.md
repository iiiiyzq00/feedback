# AI 应用开发经验与高频踩坑

## 1. Prompt Cache 优化的是前缀，不是无限上下文

- 固定规则放自动加载的稳定前缀；日期、部署状态和当前需求放后面。
- 缓存命中 Token 仍代表模型处理了长上下文。命中率高而输入量巨大时，应先压缩上下文。
- 不同模型、供应商、工具清单和 reasoning 配置通常形成不同缓存边界。没有明确收益时不要来回切换。
- 先分别统计 `cached`、`uncached`、长上下文分布和供应商，再讨论浪费；不要把 cached token 直接等同于损失。

## 2. 项目记忆必须分层

- `AGENTS.md`：长期不变的工作协议。
- `PROJECT_SNAPSHOT.md`：小型当前快照和任务路由。
- `PROJECT_MEMORY.md`：完整当前事实源，仅定向搜索。
- `delivery/`：当前交付契约；`reference/`：稳定专题知识；`archive/`：历史证据。
- 一条事实只保留一个主维护位置。复制状态数字会造成冲突，也会重复消耗 Token。

## 3. 日志不是上下文，结论才是

- 对话保留失败命令、关键错误、根因和最终处理，不保留数百行完整日志。
- 同一失败方案出现两次后停止重复尝试，先形成假设和可证伪检查。
- 跨后端、前端、部署阶段前生成交接摘要；新阶段只加载摘要和必要文件。
- Git diff 可重新获得，不要在总结中复制整个 diff；记录文件和修改目的即可。

## 4. 证据等级不能混写

- 单测中 Mock 了外部端口，只证明本系统状态机或契约。
- 本机启动、降级路径和目标环境真实集成是不同结论。
- 历史完整测试只证明当时版本，不能自动覆盖之后的代码和迁移。
- “已实现”“已部署”“已联调”“生产验收”必须分别陈述。
- 使用 `verify-delivery-claim` 技能统一校准措辞。

## 5. 数据与异步任务必须围绕权威事实设计

- MySQL 保存权威业务事实；ES/Milvus 失败只影响派生索引，不得伪造业务成功。
- 集成测试不要依赖全局队首、空库或全局数量。为每个用例创建唯一业务键并精确查询。
- 后台调度器可能与测试直接驱动的 Worker 抢任务；测试中隔离调度器并按目标 ID 原子领取。
- 通知任务写入成功不等于供应商送达；超时先查最终回执，再决定补偿。

## 6. 安全链路最容易被“测试绿”误导

- Mock 解密只证明拿到正确密钥后的逻辑，不能证明真实公私钥匹配。
- Mock 病毒扫描只证明状态流转，不能证明 clamd、病毒库和停机失败关闭。
- 脱敏、诊断信息、附件原文必须区分普通页面、受控查验和审计证据。
- 敏感响应使用 `no-store`；前端窗口关闭时清除内存；日志和导出不得保存明文。
- 密钥放环境变量、Keychain 或 Secret Manager，不放 Git 文档、项目记忆或普通配置文件。

## 7. Flyway 的历史不可修辞化处理

- 成功执行的迁移永不修改。需求变化新增前向迁移。
- checksum 异常先对照数据库历史和 Git 文件，不直接 `repair`。
- 回填必须保留来源、解析版本和失败事实；不能只留下“修好了”的结果。
- 使用 `guard-flyway-change` 技能完成迁移前检查和证据分级。

## 8. 推荐的日常节奏

1. 读短快照，检查工作区，只选一个专题入口。
2. 明确目标、非目标和验收条件，再改代码。
3. 小步实现并运行与风险成比例的测试。
4. 达到压缩门槛时生成最小交接，不携带旧日志。
5. 收尾只写完成、未完成、待核验和最多三个下一步。

把“少读、精确改、分级验、及时压缩”作为默认工程习惯，比单纯追求更高缓存百分比更能降低成本和返工。
