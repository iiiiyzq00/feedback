# 交付物 13：现场 Demo 手册

本项目交付可复现的现场 Demo，不虚构公开地址或已发布视频。历史截图和真机证据位于 `artifacts/xt11a/`，APK 可从源码重新构建。

## 1. 建议安排

建议 35–45 分钟：架构与安全边界 5 分钟，四渠道接入 12 分钟，查询/归簇/AI 10 分钟，看板报告与权限 8 分钟，提问及降级演示 5 分钟。

## 2. 演示前准备

1. 按 [交付物 02](02-local-run.md) 启动 MySQL、Redis、后端和前端，确认健康检查与 42 表。
2. 准备管理员、普通分析用户、渠道运营和隐私处理员账号；密码只在本地注入。
3. 使用 `data/test-fixtures/full-system-20260805/` 的模拟 Jira、质量平台和红黑榜文件。
4. 构建并安装 `health-demo` 或 `child-art-demo`；两个 Demo 使用独立 app key/secret，并可展示应用版本、系统版本、设备型号及允许的网络、存储、电量字段。
5. 准备一条含唯一模拟手机号/姓名/地址标记的反馈，用于验证客户端基础过滤和服务端严格脱敏。
6. 预先确认 LLM、搜索、向量、邮件和飞书是否可用；不可用时按降级方案演示。

## 3. 逐步演示脚本

| 顺序 | 操作 | 必须展示的验收点 |
|---|---|---|
| 1 | 打开交付物 04 四渠道图 | 四条独立接入流、共同脱敏门禁、分析与输出链路 |
| 2 | Demo App 提交反馈 | 客户端预过滤、环境字段、receipt、进度查询、弱网/重试说明 |
| 3 | 上传 Jira 文件 | 工作表/预览、Issue Key 幂等、旧快照跳过、批次统计和对账 |
| 4 | 上传质量文件 | 可配置表头、既有来源 ID 生成规则、校验失败和重试 |
| 5 | 上传红黑榜文件 | 红黑类型、评价周期、重复识别和来源口径保留 |
| 6 | 隐私工作台 | 普通接口只见 PASS；失败记录仅见安全元数据；必要原文查看需专门权限、理由和审计 |
| 7 | 四渠道及统一列表 | 固定来源标签、筛选、来源时间、批次、新鲜度和外部只读提示 |

## 4. 关键复测动作

- 重复上传相同 Jira Issue Key，确认更新或跳过而非新增。
- 上传更旧的来源快照，确认不能覆盖新状态。
- 用普通账号搜索隔离记录的唯一敏感标记，查询、导出、报告和 AI 均应无结果。
- 对质量平台相同组合字段重复导入，确认来源记录 ID 生成方式不变。
- 展示批次恒等式：`总行数 = 新增 + 更新 + 跳过 + 失败`。

## 5. 故障与降级演示

无 LLM Key 时展示确定性规则或结构化失败状态；无 Milvus/搜索时从 MySQL 权威数据继续普通查询或明确能力降级；无邮件/飞书时只展示待投递/失败状态，不声称送达。停止一个文件批次不能影响 SDK 和其他渠道，AI 失败不能影响接入、普通查询和程序统计。

## 6. 演示结束与证据

记录代码版本、演示时间、数据集、账号角色、关键截图和未启用的外部依赖。演示数据通过有权限的批次回滚/作废流程处理，不直接删库。真机辅助脚本为 `tools/verify-xt11a.sh`，全系统数据生成器为 `tools/generate_full_system_test_data.mjs`。

最近一次第 15 节统一验收已于 2026-08-05 15:11 在本地环境通过，现场可直接展示 `output/acceptance/section15-acceptance.md` 及其五份步骤日志。派生索引当次处于 DEGRADED，应把它作为“AI/索引失败不阻断接入、查询和回滚”的真实降级证据讲解，不应表述为 ES/Milvus 同步成功。

## 8. 演示数据位置与清理边界

生成器位于 `tools/generate_full_system_test_data.mjs` 和 `tools/generate_demo_realtime_sdk_seeds.mjs`；生成结果位于 `data/test-fixtures/full-system-20260805/` 与 `data/test-fixtures/sdk-realtime-demo-seeds-20260805/`，各目录的 `README.md` 和 manifest 说明文件、条数、哈希及预期结果。它们是仓库中的模拟输入，不等于已导入数据库的数据。

数据库演示数据应通过批次回滚/作废或经过审计的测试数据清理脚本处理，并先按批次、来源前缀和 manifest 对账确认范围。不要使用广泛 `DELETE`、清库或 Flyway clean；正式业务记录与测试记录无法可靠区分时必须停止清理并补充标识。清理后再次核对四渠道计数、批次状态、派生索引待重建状态和 42 表数量。
