# 交付物 03：产品需求与功能说明

## 1. 产品目标

平台统一接入学习机 SDK 反馈、400 Jira、质量平台和红黑榜数据，在不改变各来源业务口径的前提下完成严格脱敏、标准化、查询分析、跨渠道归簇、AI 辅助和运营治理。权威原始需求见 `../../../docs/学习机智能反馈分析与运营平台-实习生项目需求-v2.md`，本文给出与当前实现对应的交付范围。

## 2. 用户与职责

| 角色 | 主要能力 | 明确限制 |
|---|---|---|
| 普通分析用户 | 查询 PASS 数据、看板、受控导出和查看来源 | 不可查看隔离内容或原文 |
| 渠道运营 | 查看所属渠道、批次、失败明细和对账 | 不可越权访问其他渠道字段 |
| 隐私处理员 | 在隐私工作台处理失败记录和规则命中 | 仅按审批权限查看必要原文，行为全审计 |
| AI/质量复核员 | 复核低置信度分类、归簇和质量异常 | 不修改来源系统原始字段 |
| 管理员/审计员 | 权限、规则、审计和高风险操作治理 | 高风险操作仍需显式授权 |

帐号认证支持本地应急帐号与飞书 OAuth 并存。飞书只作为身份与组织事实源，平台角色、原子权限和数据范围继续由本系统裁决；首次登录创建 `SSO` 影子帐号并绑定稳定外部身份，不以姓名、手机号或邮箱作为主键。OAuth `state` 和前端登录兑换码均为短时单次凭据，浏览器会话 ID 不得放入回调 URL。开发环境可显式启用“一次性首位飞书管理员引导”，仅首个绑定身份获得 `ADMIN` 全权限，正式环境默认关闭，后续用户默认最低权限并由管理员配置。密码登录仅作为受控应急入口保留。

系统管理提供独立的“飞书权限映射”治理页面。映射对象只接受飞书稳定用户 ID、用户组 ID、部门 ID 或默认规则，显示名称仅供管理员识别，不参与权限匹配；匹配优先级固定为指定用户、用户组、部门、默认规则。用户组策略主要授予岗位角色，部门策略主要授予渠道、模块或区域数据范围，逐用户规则只作例外。规则必须先保存为 `DRAFT`，再由具备用户权限管理能力的项目负责人填写理由后批准、拒绝或退役，保存版本并写入审计日志。组织同步默认关闭；开启前必须取得飞书用户状态、所属部门和所属用户组的最小只读能力。同步只消费已批准规则，变化时更新 SSO 用户角色和自动数据范围并递增 `auth_version` 撤销旧会话；离职或停用自动禁用 SSO 帐号，外部查询失败必须 fail-safe 保持原权限并记录失败。页面支持不写库的权限模拟和同步状态展示。`ADMIN` 映射属于高风险决策，正式环境不得使用首人引导或未经审计的部门名称自动授权，本地应急帐号不得被飞书同步修改。

## 3. 渠道范围

| 渠道 | 接入方式 | 时效 | 幂等与回写 |
|---|---|---|---|
| SDK | 签名 API/上传 | 实时或准实时 | 自动来源 ID；仅更新平台处理状态 |
| 旧反馈平台 | V1/V2兼容实时入口 + 受控历史导入 | 实时或准实时，历史文件用于补数 | 旧反馈业务ID；不回写旧来源系统 |
| 400 Jira | 只读 Token API 增量拉取 + Excel/CSV 增量导入 | API按配置调度，文件用于补数/降级 | Issue Key；不回写 Jira |
| 质量平台 | Excel/CSV 导入 | 文件时效 | 既有组合键生成规则保持不变；不回写 |
| 红黑榜 | Excel/CSV 导入 | 文件时效 | 来源业务键与周期去重；不回写 |

所有渠道必须保存 `source_channel`、`source_record_id`、`source_event_time`、`source_update_time`、`ingest_time` 和 `masking_status`。

## 5. 安全不变量

1. 普通查询、搜索、看板、报告和导出始终强制 `masking_status=PASS`。
2. 非 PASS 数据只允许在隐私工作台查看非正文安全元数据；查看必要原文需要独立的高权限、理由和审计，不能由普通接口旁路。
3. 表格原始内容使用受控加密存储，仅用于隔离修复、重放或合规追溯；业务调用应使用已脱敏字段或不可逆/令牌化标识。
4. 未通过脱敏的数据不得进入分析、搜索、向量或大模型流程。
5. 五渠道任务隔离，AI 或单一渠道失败不影响普通接入、查询和统计。
6. Jira API只允许后端只读搜索；Token不进入前端、数据库、日志或源码，外部契约缺失时连接器默认关闭且文件导入继续可用。

## 6. 范围边界

必做范围覆盖需求第 12.1 节的接入、统一模型、脱敏、渠道页面、统一查询、来源标签、AI 分类摘要、相似问题和基础看板。自然语言助手、自动报告、风险预警和通知属于增强能力；私有模型、大规模处理、完整血缘及更细粒度权限属于挑战范围。增强能力不可降低必做链路的安全门禁。

开发阶段启用历史治理模式：隐私复核与归簇审核任务继续保留优先级、创建时间、到期事实和审计，但不计算逾期、不触发审核 SLA 告警；附件授权、原文保留、登录令牌等安全有效期不受影响。上线前必须显式恢复 `REVIEW_GOVERNANCE_SLA_ENABLED=true` 并核验存量任务。

Jira 查询分为“待处理问题、已解决与知识、全部数据”：未解决来源进入平台处置视图，已解决来源不进入该队列，只在证据充分时生成待人工审核的知识候选；全部数据用于追溯。Jira原始状态通过受版本治理的映射生成统一处理状态，普通业务页面只展示“处理状态”，不得再并列展示“来源状态/平台状态”两套业务字段；原始值和映射证据继续保留且不回写 Jira。SDK 列表和详情必须显式汇总截图、日志、视频等辅助分析证据，实际访问继续受安全检查、授权和审计约束。

Jira经办人、报告人、创建人和项目负责人优先使用只读Jira API返回的`displayName`展示，缺失时才回退到Jira用户名或账号标识，不展示邮箱；这些字段只用于解释来源工单流转，平台不据此修改Jira。来源渠道列只在“全部渠道”页面展示，各专用渠道页面不重复展示固定渠道名称。

平台内部当前责任人统一称为“负责人”，不得与来源字段混用；Jira 的来源字段固定称“Jira经办人”。负责人只能通过权限控制的“分发/转派”变更，系统按第7.4节的通知与回滚契约执行，任一步失败均不得形成半完成状态。分发、转派、接收、撤回、回滚和处理状态变更必须写入不可覆盖的“经办人记录”，至少保存经办人、操作时间、原负责人/新负责人、原处理状态/新处理状态、原分发状态/新分发状态及原因；列表和详情均展示当前负责人，详情提供完整经办时间轴。

分发支持目标负责人确认接收、分发人或管理员在待接收阶段撤回；撤回必须恢复原负责人（原先未分配则恢复为未分发）并追加不可覆盖记录。负责人或管理员可追加处置说明。全部渠道列表支持按负责人、仅看我的、未分发和待接收筛选，并支持最多100条的原子批量分发；负责人筛选条件互斥，防止形成无意义组合。个人站内通知对所有已登录用户开放，但分发任务仍只对目标负责人可见并保留独立已读审计；已撤回或已回滚任务不再作为待接收通知展示，但历史事实不得删除。

第三阶段增加“我的任务”工作台，汇总我负责、待我接收和已完成反馈，并按渠道、任务状态查询。开发阶段审核SLA关闭时只展示任务年龄，`dueAt/dueSoon/overdue`不得伪造为生效；上线前恢复配置后另行验收提醒。反馈状态变更必须由当前负责人或管理员填写原因；解决或关闭必须选择已解决、暂缓、无法复现、重复问题、无需处理或转知识候选之一，关闭后允许填写原因重新打开，所有动作进入不可覆盖经办记录。批量状态更新同样执行负责人、原因、处理结论和整批事务约束。

第三阶段增加平台内“需求反馈”：任何已登录用户可提交字段缺失、展示问题、流程问题、权限问题、数据异常和新需求，自动保存页面路径、筛选上下文、渠道和关联反馈ID；附件仅保存文件名、类型和大小元数据，不保存文件正文或本地路径。普通用户只看本人提出的需求，管理员和运营可统一处理并导出CSV评审清单。五渠道筛选可保存为浏览器本地演示视图，不跨账号同步。

第四阶段将渠道负责人演示反馈升级为可验收闭环。需求状态为待评审、已受理、开发中、待验收、已完成、已拒绝或暂缓；管理员和运营可设置优先级、计划版本、负责人及完成说明，提出人只可对待验收需求确认完成或填写原因退回。负责人变化、状态变化、提交验收、验收确认/退回及评论均追加不可覆盖事件；任务分配和待验收事件进入个人站内通知。Jira关联仅保存平台上下文并提供由后端配置生成的`/browse/{Issue Key}`只读外链，禁止调用Jira写接口或把平台状态、负责人、需求及验收结论回写Jira。

第四阶段增加全部渠道、SDK、旧反馈平台、Jira、质量平台和红黑榜的渠道验收工作台。管理员和运营可提交通过、有条件通过或不通过结论，历史只追加不覆盖。渠道默认字段配置采用草稿、发布、历史版本和回滚式重新发布治理；故障发生时间、问题内容、处理状态、分发状态、负责人、最近处理时间和是否解决为不可隐藏字段。个人浏览器演示视图仍与渠道发布配置隔离。开发阶段审核SLA保持关闭。

## 7. 五渠道数据与安全契约

### 7.1 页面状态模型

业务页面只保留两个状态字段：

1. **处理状态**：唯一的反馈处置状态，取值至少包括`NEW`（新建）、`DISTRIBUTED`（已分发）、`PROCESSING`（处理中）、`SUSPENDED`（挂起）、`RESOLVED`（已解决）和`CLOSED`（已关闭）。列表筛选、详情主状态、我的任务、统计和状态流转都使用该字段。
2. **分发状态**：独立描述责任分配链路，取值至少包括`UNASSIGNED`（未分发）、`NOTIFYING`（通知中）、`PENDING_ACCEPTANCE`（待接收）、`ACCEPTED`（已接收）、`ROLLED_BACK`（已回滚）和`CANCELLED`（已撤回）。它不得代替处理状态。

每个渠道的原始状态仍是不可丢失、不可由平台覆盖的来源事实，但不再作为普通页面的第三个状态字段。系统必须保存原始状态、来源更新时间、映射后的处理状态、映射规则版本、映射时间和映射结果；只有处理状态允许参与业务操作。来源没有状态、值未知或映射失败时统一映射为`NEW`并标记`UNMAPPED`证据，禁止猜测为已解决或已关闭。来源状态后续变化时可按新版本重新映射，但人工处理结论优先，自动映射不得覆盖人工已进入`PROCESSING/SUSPENDED/RESOLVED/CLOSED`的事实。来源原值和映射证据只在具备渠道追溯权限的详情审计区或导入对账中查看，不进入普通列表、默认导出或通知正文。

| 渠道 | 来源状态事实 | 初始处理状态映射原则 |
|---|---|---|
| SDK | SDK安全处理/存储状态，不等于业务处置结论 | 通过隐私门禁并进入正式内容后为`NEW`；技术接入、隐私隔离状态不映射为业务处理状态 |
| 旧反馈平台 | 旧反馈处理阶段或历史状态 | 明确已解决/已关闭才分别映射为`RESOLVED/CLOSED`，其余可处理记录为`NEW`；不回写旧平台 |
| Jira | Jira工作流状态和Resolution | 明确已解决且Resolution有效时映射为`RESOLVED`，明确关闭时映射为`CLOSED`，其余可处理Issue为`NEW`；不回写Jira |
| 质量平台 | 申请、派单、维修等来源阶段 | 仅把有明确等价业务语义的终态映射为`RESOLVED/CLOSED`，其余为`NEW`，不可把导入成功当成已处理 |
| 红黑榜 | 榜单、发布或来源记录状态 | 默认`NEW`；发布、删除或榜单类型不是平台处理结论，不能直接映射成`RESOLVED/CLOSED` |

### 7.2 渠道关键字段矩阵

列表只展示高频定位字段，详情承载完整诊断上下文；渠道不适用或真实数据长期为空的字段不渲染。SDK、旧反馈平台、Jira和质量平台共同显示问题摘要、故障发生时间、处理状态、分发状态、负责人和最近处理时间；“反馈时间”、工单创建时间、申请时间不得替代真实故障发生时间，无法提取时必须明确显示“故障时间未提供”。红黑榜不是故障工单，不设置故障时间字段，统一显示来源发布时间。

统一故障时间事实必须保存规范时间、来源时间原文、时间精度、取值来源和解析结果。解析结果区分已解析、未提供、不可可靠解析和不适用；不可解析的原文只作为受控数据事实保存，不得直接进入普通通知或日志。渠道取值顺序如下：SDK使用客户端明确上报的`source_event_time`；Jira从问题描述中的“出现故障时间”抽取，Jira创建时间只保留为来源审计字段；旧反馈平台当前尚未接通实时入口，历史表格数据暂用导出表中的创建时间作为代理故障时间并标记`STATION_HISTORY_CREATED_PROXY`，后续实时入口必须上报真实事件时间并标记客户端来源；质量平台当前源文件没有真实故障发生字段，暂用完整率100%的商返申请日期作为问题进入业务流程的代理日期并标记`QUALITY_RETURN_APPLY_PROXY`，不得用派单、激活或出货日期替代，质量渠道页面直接以“商返申请日期”命名该字段；红黑榜故障时间为不适用，页面使用`pub_time`显示发布时间。代理值不得伪装成来源明确提供的真实故障时间；后续获得同记录权威时间时，真实值优先。时间范围、模糊时间和只精确到日期/小时的值必须保留精度证据，不得伪装为精确到秒。

| 渠道 | 列表优先字段 | 详情诊断字段 | 受控字段 |
|---|---|---|---|
| SDK | 故障时间、应用、版本、机型、功能模块、处理/分发状态 | 网络、系统版本、页面路由、请求/错误上下文、崩溃堆栈、截图/视频/附件摘要 | 用户ID、手机号、设备序列号、帐号上下文、应用日志、附件正文或下载链接 |
| 旧反馈平台 | 故障时间、产品/应用、问题类型、处理/分发状态 | 设备型号、版本、补充描述、图片/附件/日志摘要 | 用户ID、联系方式、设备序列号、原始正文、附件和日志内容 |
| Jira | Issue Key、故障/来源更新时间、优先级、Jira经办人、版本、模块、处理/分发状态 | 报告人、创建人、项目负责人、描述、评论摘要、Resolution、只读来源链接和日志证据 | 描述/评论中的受保护内容、设备身份、日志和受控原文；不展示邮箱 |
| 质量平台 | 商返单号、产品名称、产品型号、故障现象、区域、处理/分发状态 | 派单时间、激活时间、维修/换机上下文和来源阶段 | 机身号码/设备序列号、用户身份、联系方式和原始导入行 |
| 红黑榜 | 发布时间、作者、来源平台、榜单类型、情感、处理/分发状态 | 正文摘要、评价对象/维度、数据周期和原文链接 | UID、原始正文、可识别身份信息和受控来源链接 |

内部数据库ID、哈希、密文、来源记录ID和无法被业务人员理解的产品ID不得作为默认业务字段；它们必须继续保留用于幂等、血缘和审计。功能模块只有在权威渠道值、人工结论或满足受控提升规则的AI分类存在时展示正式值，否则显示“待分类”。

### 7.3 敏感诊断信息查验

普通页面只返回完成判断所需的脱敏信息。用户ID、手机号、设备序列号、帐号上下文、日志详情、附件原文和来源原文分别受字段权限控制，不能因拥有某一项权限而自动获得其他项。页面按当前角色权限直接展示，不存在“受控查看”或填写用途/理由的产品流程；服务端仍实时鉴权并记录查看人、固定动作码、时间、对象、字段类别、权限依据、IP和结果。响应使用`Cache-Control: no-store`，不得进入普通日志、站内通知、搜索索引、AI输入或默认导出。关闭查看窗口、切换反馈或离开页面时必须清除前端内存中的明文。日志与附件使用一次性或短时安全流，不返回可长期复用的真实存储地址。

身份、联系方式、设备及从SDK安全处理阶段提取出的诊断事实采用独立AES-GCM密文长期留存、受控解密和访问审计；禁止再以业务处理完成为由删除这些权威诊断密文。SDK应用日志、帐号上下文和私有文件清单必须组成独立诊断密文包，普通渠道表对应明文字段保持为空。SDK主体大信封、Station原文和导入原始行仍按各自隐私复核与重放目的执行独立保留期；拥有诊断查看权限不等于拥有整包原文查验权限，反之亦然。生产环境必须使用KMS/Secret Manager并完成密钥轮换演练；生命周期变化只能通过新的前向Flyway迁移实施，禁止修改已执行迁移。

### 7.4 分发与通知原子性

分发替代主动认领。只有获得分发权限的人员可以选择接收人或处理组，并记录分发人、接收人、原因、前后负责人、处理状态、分发状态和幂等键。分发先进入`NOTIFYING`；站内通知任务、负责人变更、处理状态转为`DISTRIBUTED`、分发状态转为`PENDING_ACCEPTANCE`以及不可覆盖审计必须在同一数据库事务中成立，通知任务写入失败时整笔分发回滚。

页面必须把分发和转派作为两个清晰的业务动作展示：尚无平台负责人时只能执行“分发”，已有平台负责人时更换负责人只能执行“转派”。列表、批量操作、详情按钮、弹窗标题、原因字段、确认按钮和结果提示均不得再使用“分发/转派”合并文案。两者可以复用同一套负责人变更、通知任务和失败回滚事务能力，但操作前必须按当前负责人事实校验适用动作；批量操作不得混合未分发与已有负责人的记录。

若实际通知投递在事务提交后异步完成，最终投递失败必须通过幂等补偿事务恢复原负责人和原处理状态，将分发状态记为`ROLLED_BACK`，并保留失败与补偿审计；不得物理删除已发生的分发尝试。批量分发最多100条且整批原子，任一通知任务创建或最终投递失败均整批回滚或整批补偿。通知超时不得直接视为失败，必须先按供应商幂等键查询最终回执，避免通知实际送达但平台误回滚。补偿失败必须进入可重试任务和运维告警。

分发后的人工提醒/催办是独立业务动作，不得重复分发或改变负责人、处理状态及分发状态。具备分发权限的原分发人、当前负责人所属团队的负责人或管理员，可对已有负责人且尚未解决/关闭的任务发起提醒：`PENDING_ACCEPTANCE`使用“提醒接收”，其余有效处理中状态使用“催办处理”。系统必须以幂等键原子写入独立催办事实、站内通知和不可覆盖经办记录，保存催办人、当前负责人、原因、说明、处理/分发状态快照及时间；同一任务与当前负责人30分钟内只允许成功催办一次。转派后不得继续提醒旧负责人，撤回、回滚、未分发、已解决或已关闭任务不得催办。催办投递失败只重试催办通知，不得回滚既有分发；通知正文不得包含受控诊断原文。

## 8. 验收标准

- 用模拟数据完整跑通 SDK 和三个文件渠道；来源标识、批次、幂等、旧快照、失败与对账均可验证。
- 用唯一敏感标记证明非 PASS 内容不会进入普通查询、日志、索引、向量和 AI。
- 看板同时说明渠道口径、新鲜度、原始记录数与去重问题数。
- AI 故障或外部索引不可用时，接入、MySQL 查询和程序统计继续工作。
- V218后56张物理业务表治理基线、权限边界和审计记录通过自动化或现场核验。
