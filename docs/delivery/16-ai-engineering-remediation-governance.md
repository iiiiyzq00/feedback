## 1. 治理目标

本轮不是继续补功能，而是先把项目从难以阅读、难以验证、无法稳定上线的状态，重构为可以由工程师持续维护的企业级系统。

必须同时关闭两类问题：

1. **代码治理**：直接 SQL、多表业务查询、层次混乱、接口弱类型、注释缺失、权限逻辑分散和不可审核的 AI 大批量修改。
2. **产品与页面治理**：文件落本地、信息隐藏在多余操作之后、媒体和日志不可直看、字段优先级错误、问题分类不可解释以及不同应用边界丢失。

执行顺序固定为：

1. 用户确认一期范围内的代码类问题已经解决，作为一期页面治理的准入事实；该确认只改变阶段顺序，不等于生产就绪证明。
2. 优先完成一期页面与产品治理：P1 文件与附件架构、P2 页面信息架构与媒体体验、P3 归簇可解释性和准确性。
3. 完成一期 P4 跨栈、用户和目标环境验收，由用户确认一期页面治理关闭。
4. 再恢复并完成全仓 C0-C5 代码治理及其退出门禁。

2026-09-01 前已产生的 C0 候选、基线和验证事实必须保留，暂停期间不得删除、放宽或伪造关闭；一期 P4 关闭后从当时的真实状态继续全仓治理。未经用户重新确认，不得再次调整该顺序。页面治理虽先行，但不得新增直接 SQL、多表业务查询、弱类型接口、分散权限逻辑或其他全仓治理债务，也不得借页面任务扩大到未批准的全仓重构。

- 约 64 个文件出现 `JOIN`。

- 部分 Controller/Service 使用 `Map<String, Any?>` 作为对外或跨层契约。
- 项目已有 Spring Security、过滤器和部分集中授权，但数据权限、字段权限和操作者解析仍在部分业务 Service 中重复处理。

## 3. 全项目不可变架构规则

### 3.1 SQL 与 MyBatis 边界

所有现有直接 SQL 都是必须清零的技术债。配置生效后禁止新增：

- Controller、Service、Repository 实现、任务、监听器、过滤器中的 SQL 字符串。
- `JdbcTemplate`、`NamedParameterJdbcTemplate`、native query 或其他绕过 Mapper 的直接 SQL 执行。
- Kotlin、Java、TypeScript、JavaScript、测试、SDK、Demo 和普通脚本中的 SQL 拼接或执行。
- 为了绕过静态检查而拆分、编码或动态拼装 SQL。

SQL 只允许存在于以下受控边界：

1. MyBatis Mapper/XML。
2. 尚未应用的 Flyway 前向迁移。
3. 明确标识用途、权限、回滚与验证方式的运维 SQL。

已应用 Flyway migration 永远禁止编辑。需要变化时新增前向迁移。

MyBatis 采用标准可持续依赖，不直接复制 Station 的私有 `mybatis-component`。参考 Station 的 Mapper、Repository、查询对象和公共拦截思想，同时使用当前 Spring Boot/Kotlin 版本支持的实现。

### 3.2 单表查询与代码组装

业务查询必须为单表查询，禁止：

- 多表 `JOIN`。
- 跨表相关子查询。
- 数据库视图或存储过程伪装的多表业务查询。
- 循环内逐条查库形成 N+1。
- 把整库数据加载到内存后再分页。

统一查询方式：

1. 在主实体表完成过滤、稳定排序和分页。
2. 收集当前页需要的关联主键或业务键。
3. 对每张关联表执行一次有界批量单表查询。
4. 使用明确类型在应用层 `associateBy`、`groupBy` 或领域聚合器中组装。
5. 对批量大小、空集合、重复键、缺失关联和顺序稳定性编写测试。

统计查询同样按单表计算事实，再由代码组合。MySQL 仍是权威事实源；Elasticsearch 和 Milvus 只能作为可重建派生索引。

### 3.3 分层与对象边界

默认调用方向：

```text
Controller -> Application Service -> Domain/Assembler -> Repository -> MyBatis Mapper -> 单表
```

职责要求：

- Controller：协议适配、参数校验、调用应用服务，不包含查询和业务流程。
- Application Service：编排用例、事务和领域协作，不感知 SQL。
- Domain/Assembler：业务规则和跨表结果组装，不访问网络或数据库。
- Repository：表达领域需要的数据能力，协调单表 Mapper，不返回通用 Map。
- Mapper：单表持久化，不包含业务规则和权限猜测。

接口对象必须区分：

- `XxxRequest`：HTTP/RPC 请求。
- `XxxResponse`：HTTP/RPC 响应。
- `XxxQuery`：查询条件。
- `XxxCommand`：写操作意图。
- `XxxDTO`：应用层传输。
- `XxxPO`：持久化对象。
- 领域对象：业务状态和不变量。

禁止用 `Map<String, Any?>`、数据库行 Map、PO/Entity 或无字段约束的 JSON 作为公开 API 或稳定跨层契约。

### 3.4 接口与字段说明

每个公开接口必须有明确请求、响应和错误契约。每个字段至少说明：

- 中文业务含义。
- 是否必填和默认值。
- 类型、长度、格式、单位和时区。
- 枚举含义和未知值策略。
- 示例值。
- 脱敏、权限和审计要求。
- 与来源字段的映射关系（需要追溯时）。

请求对象使用 Bean Validation；响应字段通过 OpenAPI/Schema 或等价契约生成可审阅文档。接口契约测试必须覆盖字段名、必填性、分页、排序、空值、权限和错误码。

### 3.5 注释和可维护性

必须注释：

- 类的职责、边界和协作者。
- 复杂流程每一步的输入、输出和状态变化。
- 业务不变量、幂等、事务、并发和失败关闭策略。
- 权限、隐私、脱敏、审计和安全设计。
- 看似可简化但不能简化的原因。
- 算法参数、阈值来源及其业务影响。

禁止以注释数量代替可读性。无意义注释、过长单行、压缩式“一行完成所有逻辑”、模糊命名和混合职责类都必须在审核中拦截。

### 3.6 通用权限组件

权限按四层收口：

1. 认证过滤器建立统一主体。
2. 路由授权控制接口访问。
3. 方法/用例授权声明业务动作。
4. 数据范围与字段策略组件提供渠道、模块、区域、原文/局部隐藏和审计上下文。

Controller、Service 和 Mapper 不得自行解析 Token、推断角色或复制权限分支。Mapper 接收已经确定的单表数据范围参数，但不得自行扩大范围。

权限变更至少验证：

- 已认证且授权成功。
- 未认证拒绝。
- 已认证但无权限拒绝。
- 渠道、模块和区域隔离。
- 技术/产品字段可见性差异。
- 直接 ID 访问不能绕过列表范围。
- 审计事实完整且无秘密泄漏。

## 4. 页面与产品治理规则

本节先在一期范围实施，准入依据为用户已确认一期代码类问题解决；一期页面治理关闭后，规则继续作为全仓页面与产品开发的不变量，并在后续 C0-C5 重构中不得被破坏。

### 4.1 文件与部署

- 图片、视频、日志和其他附件禁止把源文件作为长期事实保存在应用服务器本地磁盘。
- 权威记录保存对象存储键、受控链接、来源附件 ID、完整性、安全状态、大小、类型和生命周期。
- 浏览器不得获得永久公开地址；通过实时鉴权的短期链接或受控流访问。
- 本地开发只能使用与对象存储接口兼容的测试适配器，不能把本地路径写成生产语义。
- 上传、同步、扫描、隔离、过期、删除和重新拉取必须可审计、幂等和失败关闭。

### 4.2 信息直接展示

- 页面关键信息直接展示，不依赖多余点击、悬停、复制或展开才能理解。
- 图片和视频按当前角色权限直接显示缩略图、加载状态、失败原因和预览，不要求填写查看理由。
- 日志在页面内展示有界文本预览并标明截断。ADMIN/具备 RAW 权限的技术角色可通过独立的 `ORIGINAL_LOG_DOWNLOAD` 一次性用途令牌下载原始日志或未解压压缩包；产品角色禁止下载。下载授权无用户理由输入，但必须实时复核权限、归属和安全状态并记录审计；预览令牌与下载令牌不可互换。
- 问题内容完整换行展示；操作只保留真正必要的动作。
- 学习机 Android 版本移入详情，不占用高优先级列表空间。
- 字段顺序、默认可见性和空值表达通过页面契约测试冻结。

具体 UI 在实现前单独形成线框/字段表并由用户确认；未经确认不得用代码反复试布局。

### 4.3 问题分类与应用边界

必须建立唯一的归簇流程文档，逐步骤记录：

1. 原始来源输入。
2. 安全正文与清洗输出。
3. 应用身份解析结果。
4. 原子问题/对象/动作/现象/错误签名画像。
5. 全文、向量、签名和结构化候选召回输入输出。
6. 硬冲突和应用边界过滤。
7. 模型输入、候选集合、输出和校验。
8. 确定性回退。
9. 最终簇、名称、成员和审计落库。
10. 列表、详情和统计读取口径。

每一步必须给出真实脱敏样本、参数、输入输出结构、丢弃原因和可复现调试方式。

应用身份是归簇核心维度：相同描述发生在不同应用时默认是不同问题簇，除非经过明确批准的跨应用产品语义证明可以合并。簇名称和抽象必须指出“哪个应用的什么功能出现什么问题”；簇详情和调试事实必须展示具体应用。

## 5. AI 开发强制流程

### 5.1 任务进入

每个任务先完成：

1. 读取项目快照和本合同。
2. 只读取当前任务路由的一个交付/参考文档。
3. 运行上下文脚本并检查任务路径状态。
4. 将所有无关改动视为用户资产。
5. 明确本次属于一期页面治理、全仓代码治理还是验证；当前必须先关闭一期 P1-P4，之后才能恢复全仓 C0-C5，任何阶段都不得越过前一阶段的用户验收门禁。

### 5.2 方案审批门禁

方案必须先于代码，至少包含：

- 用户问题和成功标准。
- 当前调用链、逐步输入输出和确定证据。
- 涉及文件、接口、表和外部依赖。
- 目标分层和对象设计。
- 每张表的单表查询与批量组装方式。
- 权限、隐私、审计、事务和并发边界。
- 兼容性、数据迁移、回滚和部署影响。
- 测试矩阵和未验证风险。
- 明确不在本批次处理的内容。

用户未明确批准前，只能做只读审计和方案修订，不得修改业务代码。实现中发现会改变上述内容的新事实，立即暂停并重新审批。

### 5.3 小批量实现

- 一个批次只解决一组明确边界的问题。
- 先写或冻结行为特征测试，再重构。
- 不顺手改页面、不顺手改数据库、不顺手扩展功能。
- 机械迁移使用生成器或受控脚本；业务语义由人工可读代码表达。
- 删除或替换旧路径前证明新路径行为、权限和数据口径一致。
- 不为了让测试通过而降低断言、扩大权限、绕过安全门禁或伪造外部集成。

### 5.4 审核和用户验收

每个批次按固定顺序结束：

1. 作者视角自审：正确性、边界、可读性、安全、性能和测试。
2. 自动验证：定向测试、静态检查、`dev-check` 对应级别。
3. 独立审核视角重新读取批准方案和实际 diff，不沿用实现时的合理化结论。
4. 按优先级修复审核发现并重新验证。
5. 向用户提交文件清单、接口/数据变化、验证证据、未验证风险和重点审核项。
6. 用户确认后关闭批次；未确认不得进入下一批。

## 6. 分阶段改造计划

### 阶段 P1：一期文件与附件架构

- 设计并实现对象存储链接模型、迁移、访问、安全和生命周期。
- 不得把应用服务器本地源文件或永久公开地址作为生产事实。

### 阶段 P2：一期页面信息架构与媒体体验

- UI 方案先审批，再实现直接展示、缩略图、日志预览和字段优先级。
- 冻结列表、详情、空值、加载、错误、权限和直接预览契约。

### 阶段 P3：一期归簇可解释性和准确性

- 用逐步输入输出文档和真实脱敏样本定位误差。
- 强化应用边界、簇名称、详情应用字段和跨渠道同类问题分析。

### 阶段 P4：一期跨栈与上线验收

- 完成作者自审、自动验证、独立代码审核、用户验收和目标环境证据。
- 本机、Mock、降级、静态或测试库结论不得写成生产成功。
- 用户明确确认一期页面治理关闭后，才恢复全仓 C0-C5。

### 阶段 C0：全仓治理门禁

- 建立直接 SQL、JDBC、JOIN、Map API、接口文档和权限测试的静态基线。
- 现有债务必须形成精确清单，只能减少；所有新增违规立即失败。
- 冻结全项目关键接口和权限行为。

### 阶段 C1：全仓数据访问基础设施

- 接入标准 MyBatis。
- 建立 PO、Mapper、Repository、Query/Command 和事务规范。
- 用一个低风险垂直样例验证 Kotlin、分页、批量查询、事务和测试约定。

### 阶段 C2：全仓公共认证与权限

- 收口主体、接口授权、数据范围、字段策略和审计上下文。
- 移除业务层重复权限代码并完成拒绝矩阵。

### 阶段 C3：全仓业务模块数据访问迁移

- 按模块迁移所有直接 SQL 和多表查询。
- 每批迁移后减少技术债基线，直到全仓归零。
- 一期模块优先不代表其他模块可以永久保留违规。

### 阶段 C4：全仓接口、对象、注释和代码结构收口

- 清除公开 Map、持久化对象泄漏和未说明字段。
- 拆分巨型类和混合职责，补齐有效注释和契约测试。

### 阶段 C5：全仓代码治理总验收

- 全仓直接 SQL/JDBC 为零（受控 SQL 边界除外）。
- 业务 JOIN、跨表子查询和 N+1 为零。
- 对外弱类型接口为零。
- 权限重复实现为零。
- 静态、快速、完整和目标环境所需门禁达到各自声明范围。
- 用户明确批准全仓代码治理退出；后续页面变更继续遵守本合同，但不再设置重复的一期页面前置阶段。

## 7. AI 成本控制

- 一个任务只读快照、本合同和一个任务文档。
- 每批最多三个下一步，完成后压缩上下文。
- 方案任务与实现任务分离；无批准不生成代码。
- 静态清单、接口差异、重复规则和债务计数由脚本生成，不让模型反复人工扫描。
- 先冻结契约再重构，减少“修完再猜原行为”的返工。
- 不把完整日志、全量 diff、历史归档和生成物送入上下文。
- 不以更换模型、增加推理或多代理代替明确边界和可复现测试。

## 8. 完成定义

“功能能运行”不等于完成。一个批次只有同时满足以下条件才可提交用户审核：

- 与批准方案一致，未暗中扩大范围。
- 所有输入、输出、状态、权限和失败路径可解释。
- 代码符合本合同的 SQL、分层、类型、权限和注释规则。
- 新旧行为差异有明确合同和测试。
- 自审与独立审核均已完成，发现已关闭或明确阻塞。
- 验证证据按静态、本机、集成、目标环境和生产正确分级。
- 项目快照/记忆已同步，下一步不超过三个。

任何一项缺失，都只能表述为“进行中”或“阻塞”，不得表述为完成、可上线或生产就绪。
