# 交付物 07：Jira API/文件、质量平台和红黑榜导入

400 Jira支持两种并存入口：后端使用Token执行只读API增量拉取，Excel/CSV继续用于历史补数、人工修复和API不可用时降级。两种入口都写入`source_channel=JIRA`，以Issue Key为统一业务键，不建立`JIRA_API`新渠道，也不向Jira回写。

三渠道的业务键、更新时间、特有字段和重复处理对照见 `../reference/technical-architecture.md` 第 3 节；安全和容量验收见 `../archive/acceptance/topic04-table-import-privacy-final-acceptance.md`。

## 1. 共用导入流程

```mermaid
flowchart LR
  U["上传/分片暂存"] --> V["文件、工作表和表头边界校验"]
  V --> P["脱敏预览与映射推荐"]
  P -->|"精确匹配"| Q["自动进入处理队列"]
  P -->|"表头漂移"| M["人工确认映射并发布新版本"]
  M --> Q
  Q --> R["加密行分片处理"] --> K["业务键、指纹和更新时间判断"]
  K --> D["脱敏和标准化"] --> C["渠道适配器落库"] --> X["批次对账"]
```

支持 CSV、XLS、XLSX、工作表选择、最多 20MB 文件、最多 50,000 行和 200 列。大于 5MB 的文件必须走加密分片暂存，后台 worker 负责组装和解析。

## 2. Jira 增量策略

- `Issue Key` 映射为 `source_record_id`，是业务幂等键。
- 文件 SHA-256 先识别完全相同文件，但不能代替 Issue Key。
- 行指纹相同记为重复跳过。
- 导入更新时间早于已存在 `source_update_time` 时记为旧快照跳过。
- 较新快照更新状态、优先级、解决结果、版本和允许的来源字段。
- 更新时间缺失且内容冲突时记录幂等冲突事实，不静默覆盖。
- 关闭、解决和删除标记以文件快照为准；平台不回写 Jira。

### 2.1 Jira API只读拉取

- API返回字段和Jira表格共用当前已发布的Jira字段映射版本，再写入同一加密暂存行和批次Worker；不得直接旁路写渠道表或另建API专用映射版本。
- Token只由后端运行配置或秘密管理系统注入；前端、数据库、源码和普通日志均不保存Token。
- 每轮查询使用固定上界以及`updated ASC, id ASC`顺序；从上次成功水位向前重叠受控分钟数，重叠记录继续由Issue Key、行指纹和来源更新时间去重。
- 成功批次默认每30分钟推进一次增量计划；可通过`JIRA_400_SCHEDULE_INTERVAL_MINUTES`按环境覆盖。5分钟水位重叠窗口独立保留，用于覆盖边界更新并由幂等规则去重。
- 全部分页结果安全持久化为API批次后才推进水位；单行格式或隐私失败归属该批次，不阻塞后续渠道任务。
- 401/403失败关闭；429遵循受控`Retry-After`；网络和5xx错误采用持久化有界退避。错误事实不得包含Token、原始响应体或未脱敏正文。
- 首次拉取默认有回看范围和单轮数量上限；大规模历史补数必须显式缩小时间窗口，不能无边界全量拉取。
- API批次记录`ingest_method=API`及`MANUAL/SCHEDULED/BACKFILL`触发类型；文件批次保持`ingest_method=FILE`。
- API批次推进水位后禁止沿用文件批次的删除式回滚；纠错通过指定时间窗口补数重新读取Jira权威快照，避免回滚后水位越过导致数据缺失。
- 外部API契约未取得前，`app.jira400.enabled=false`，状态页显示未就绪，现有文件导入保持正常。
- Jira硬删除无法仅靠增量搜索可靠推断；删除/归档对账须在真实契约提供专门语义后启用，当前不伪造删除结果。

### 2.2 API字段复用

API字段与表格字段由同一个已发布版本维护，映射方向保持为`平台目标字段→Jira来源字段`，例如`source_record_id→key`、`jira_issue_id→id`、`title→summary`、`description→description`、`source_event_time→created`、`source_update_time→updated`。自定义字段直接在该版本中填写`customfield_xxx`，不再通过运行配置维护第二份映射。每次同步开始时锁定版本和映射快照，搜索请求字段、JSON解析和批次处理均使用该快照；历史批次不受后续版本发布影响。Cloud ADF与普通文本统一提取为待脱敏文本；经办人、报告人、创建人和项目负责人作为受控结构化流转身份保留Jira `displayName`，不保存邮箱，标题、描述、评论和环境等自由文本继续执行隐私脱敏。

### 2.3 待外部契约配置

真实联调前必须通过秘密/运行配置提供`JIRA_400_BASE_URL`、`JIRA_400_ALLOWED_HOSTS`、`JIRA_400_API_TOKEN`、`JIRA_400_AUTH_TYPE`、`JIRA_400_SEARCH_PATH`和`JIRA_400_JQL`，确认GET/POST搜索方式及分页上限，并发布包含真实标准字段/`customfield_xxx` ID的Jira映射版本后，再设置`JIRA_400_API_ENABLED=true`。连接参数不承载字段映射；映射版本不得把Issue Key、来源更新时间或人员字段映射到不安全目标。Basic模式的Token值必须由秘密系统提供已经受控编码的凭据，本平台不在日志或数据库中展开它。

## 3. 质量平台策略

- 优先使用来源问题编号；缺失时继续使用既有组合：客户地址、故障现象确认、商返申请日期生成 `QUALITY-<sha256-prefix>`。
- 来源同时提供商返单号和设备序列号时，优先以“标准化商返单号 + `DEVICE_SN`受控指纹”生成不可逆 `QUALITY-<sha256-prefix>`。单个商返单可包含多台设备，禁止仅以商返单号去重；设备序列号明文不得进入业务键或普通页面。
- 只有商返单号或设备序列号任一缺失时才回退到既有地址、故障、日期组合键，保持旧模板兼容。
- 精确地址只参与业务键和行政区泛化，正式渠道表不保存原始地址。
- 支持维修区域、省市区、申请类型、换货、退货原因、故障确认和出货日期等字段。
- 质量业务键生成算法不随表头别名、模板或枚举版本改变。

## 4. 红黑榜策略

- `source_record_id` 是正式业务键；数据周期作为来源口径保留，不替代业务键。
- 保留红/黑榜类型、评价对象、评价维度、影响等级、周期、来源部门/角色脱敏标识。
- 正负向分别统计；跨渠道分析只能通过统一字段和问题簇关联，不直接将不同样本数量相加。

## 5. 失败、重试和回滚

格式/必填/枚举/时间错误保存安全失败码与修复建议；技术失败和业务失败区分重试。成功行及时销毁不再需要的原始行密文。回滚受角色、状态和时间窗口约束，只软删除正式内容并保留对账和审计事实。

## 表头变化适配

1. 每个渠道维护可发布、带版本的模板和允许目标字段集合。
2. 上传时先识别工作表和渠道边界，再根据表头别名推荐映射。
3. 表头与当前模板完全一致且必填目标齐全时自动绑定版本；出现新增、缺失或非空未映射列时进入 `AWAITING_MAPPING`。
4. 用户确认映射后发布下一模板版本；历史批次继续保存并使用自己的 `mapping_template_id`、`mapping_config_version` 和映射 JSON。
5. 枚举别名按渠道和字段从 `t_system_config` 加载，在批次开始时合并并冻结为`enum_mapping_version`和完整 JSON 快照；目标值必须命中允许集合，非法活动配置失败关闭，未命中来源值记录安全转换事实。
6. 失败批次只有在提交映射与原快照完全相同时才属于技术重试；映射发生变化必须发布并绑定新版本。

质量平台来源记录 ID 生成规则保持不变。文件哈希只识别完全相同文件，不能替代业务键幂等。

## 6. 渠道差异矩阵

| 项目 | 400 Jira | 质量平台 | 红黑榜 |
|---|---|---|---|
| 必要业务键 | Issue Key | 问题编号或既有组合键 | 来源键/周期组合 |
| 更新时间保护 | 来源更新时间严格比较 | 数据日期/来源更新时间 | 所属周期与来源更新时间 |
| 专属字段 | 状态、优先级、解决结果、版本 | 缺陷号、严重度、负责人 | 红黑类型、对象、维度、周期 |
| 人员处理 | 经办人/报告人/创建人/项目负责人显示受控`displayName`；自由文本中的姓名继续脱敏 | 负责人、账号令牌化 | 来源部门/角色脱敏标识 |
| 口径限制 | 文件快照，不冒充实时 Jira | 缺陷/质量样本 | 运营评价样本，正负向分开 |

## 7. 失败处置边界

失败分为业务校验失败、隐私失败和技术失败。业务失败必须修正行或映射；隐私失败只在隐私工作台按受控流程处理；技术失败可保持同一批次和业务键重试。每次重试都重新执行校验与脱敏，不能复用绕过门禁的旧结果。

回滚仅撤销该批次实际产生、且之后未被更新的数据变更；存在后续批次依赖时拒绝或要求先处理依赖。作废保留批次、对账与审计事实，不物理抹去治理记录。

## 8. 验收清单

1. 相同文件二次上传被识别，但最终幂等仍由业务键决定。
2. 相同业务键的新快照更新，旧快照跳过。
3. 单行格式错误不阻断同批次合法行。
4. 非 PASS 行在查询、搜索、看板、导出、报告和 AI 中均不可见。
5. 批次满足对账恒等式，待复核行有明确归属。
6. 失败行下载不包含未经脱敏的正文或原始人员信息。
7. 回滚/作废权限不足返回 403，并写安全审计。
