# 一期智能反馈分析与运营平台近期改动契约

> 状态：已确认需求基线，开发中。生效日期：2026-08-21；问题深度分析双明细口径补充确认：2026-08-24。
> 本文是近期一期简化改动的唯一需求入口；开发阶段、阻塞和下一步只维护在 [`../PROJECT_PHASE_ONE_MEMORY.md`](../PROJECT_PHASE_ONE_MEMORY.md)。既有产品文档与本文冲突时，一期页面和权限范围以本文为准，安全与隐私不变量仍以既有交付文档为准。

## 1. 一期目标与范围

一期本轮主要改动集中在两个业务模块：

1. **渠道数据查看**：学习机反馈、Jira 反馈、质量平台、红黑榜及承载这些渠道的必要导航/详情能力。
2. **问题深度分析**：面向全渠道反馈的去重问题簇分析与明细。

“主要改动集中在两个模块”不等于系统只保留这两个模块，也不授权批量隐藏或删除未被本文逐项点名的既有导航、页面和能力。通用反馈 SDK 的实时数据纳入“学习机反馈”统一产品入口，但不恢复独立 SDK 渠道页面；AI 分类/人工分类复核前置门禁，以及本文逐项标记删除的运营、处置和分析板块不进入本轮；隐私人工复核则按第 6 节明确删除。未被明确点名的既有能力保持现状。页面删减与后续飞书权限是两个实施阶段：先完成明确的功能和字段删减，再单独实施权限收口，不得用隐藏全部其他模块代替权限控制。

## 2. 渠道与数据口径

### 2.1 学习机反馈合并

- 将通用“SDK 反馈”和 `STATION_FEEDBACK`（旧反馈平台实时反馈及历史数据）合并为一个页面，页面名称统一为 **学习机反馈**。
- 页面数据同时包含 SDK 实时上报、旧反馈平台现有历史数据，以及后续可靠双写链路进入新平台的数据。
- 通用反馈 SDK 纳入一期统一学习机入口，但不作为独立渠道页面展示。
- 合并仅改变一期产品入口和查询口径；来源渠道、来源记录 ID、来源时间、双写幂等和审计事实必须继续保留，便于追溯与去重。
- 后台继续分别保存 `SDK` 与 `STATION_FEEDBACK` 渠道码及各自扩展表、认证、任务和审计；前端固定聚合查询两种来源。问题深度分析计算“跨渠道”时，两者共同折算为一个逻辑渠道 `LEARNING_MACHINE`，不能仅因同簇同时存在 SDK 与 Station 记录就判定为跨渠道。

当前代码接入形态：

- 实时入口兼容 V1 `/v1/feedback` 与 V2 `/v1/feedback/new`；RPC 入口在双写配置启用且就绪时进入可靠双写任务，依次写入原反馈平台与新平台，并保留幂等、加密暂存、分支状态和重试事实。
- 历史数据通过受控的一次性旧平台导出文件导入器进入，用于初始历史导入和受控恢复；它不是面向普通用户的常驻表格上传入口。
- “代码具备双写能力”不等于目标环境已经启用或完成真实联调；部署时仍须核对开关、旧平台目标、密钥、积压任务和双端成功状态。
- 产品可见名称统一为“学习机反馈”，底层 `STATION_FEEDBACK` 渠道码、表名和审计来源保持不变，不做破坏性重命名。

### 2.2 全渠道含义

问题深度分析中的“全渠道”指一期纳入的学习机反馈、Jira、质量平台和红黑榜四个产品渠道；其中学习机反馈包含 `SDK` 与 `STATION_FEEDBACK` 两个可追溯后台来源码。问题簇必须跨渠道汇总，不能按单渠道分别生成后再冒充全渠道结果。

## 3. 所有渠道列表的统一删减

所有渠道页面均执行以下约束：

- 删除列表上方的概览/指标卡片，包括截图一所示“旧平台反馈、待推进处置、带分析证据、最近接入时间”等卡片。
- 筛选区只保留：
  - 搜索标题、描述或来源编号；
  - 时间相关控件；
  - 导出。
- 删除其他筛选条件、批量操作和视图配置入口。
- “操作”列只保留 **详情**；删除分发、转派、提醒、催办、状态操作、复制及其他行内操作。
- 问题内容在表格中必须完整显示，不做省略号截断，也不依赖悬停或展开操作才能阅读。实现时需用换行、自适应行高和合理列宽保证可用性。
- 导出必须沿用权限、脱敏和审计约束；页面删减不能成为敏感字段导出的旁路。

以下顺序即默认列顺序。未列出的现有业务列在一期列表中删除；来源原始事实和审计字段默认只是不展示，不代表删库。

### 4.1 学习机反馈

1. 故障发生时间
2. 问题内容（完整显示）
3. 应用名称
4. 来源平台
5. 关键信息
6. 分析证据

字段口径：

- **分析证据**：统一承载截图、日志及其他附件的直接查看入口；日志不得同时在“关键信息”中重复展示。日志统一以内联文本查看；GZIP/ZIP/TAR/TGZ 及安全嵌套日志归档由服务端有界展开，只展示可读文本条目，不得把归档头或二进制当文本。ADMIN/具备 RAW 权限的技术角色可在预览工具栏直接下载原始日志或未解压原始压缩包，产品角色无下载入口且服务端返回 403。原始下载使用无理由输入的独立固定用途令牌和 `ORIGINAL_LOG_DOWNLOAD` 审计，不复用预览流。截图或视频点击后必须立即展示加载状态，关闭弹窗即取消请求；超时、授权失效、文件缺失或清理、服务异常和浏览器不支持的媒体编码必须给出明确反馈，不能静默无响应。

## 5. 问题深度分析

### 5.1 查询区和删除项

- 默认分析**全部历史数据**，用户主动选择时间范围后才按所选区间过滤；重置恢复全部历史口径。
- 只保留时间选择，不保留其他筛选框。
- 保留两个按钮：**分析** 和 **重置**。
- 删除截图二所示“当前口径去重问题数、当前口径跨渠道问题数”等概览卡片。
- 删除以下全部板块：
  - 所有分析统一时间对比（本期 vs 上期）；
  - 严重度趋势；
  - 应用版本问题量对比；
  - 省份热度排名及其下钻；
  - 可重现性分布及其下钻。

### 5.2 全部去重问题簇明细

重新设计“全部去重问题簇明细”，每行代表一个统一归簇口径下的问题簇，而不是一条反馈或单渠道统计。该列表包含所选时间范围内的全部问题簇，包括当前仅命中一个渠道的问题簇；跨渠道子集另见第 5.3 节。

必保留/新增字段按以下顺序作为一期建议基线：

1. **问题簇现象**：从簇内所有反馈抽象得到的稳定问题现象，不能直接复制某一条反馈标题，也不能使用渠道特有措辞冒充簇定义。
2. **反馈记录数**：该簇命中的反馈总数。
3. **用户数量**：按受控、稳定且跨来源可解释的用户标识去重；无法识别的记录不得虚构用户数。
4. **设备数量**：按簇内可用的受控设备序列号（`DEVICE_SN`）指纹去重；没有设备序列号的簇显示 0，不读取或暴露 SN 明文。
5. **影响应用**：簇内涉及的应用名称集合或 Top 项，避免展示内部产品哈希。
6. **首次发生时间**：当前选择时间范围内该簇最早故障发生时间或来源发布时间。
7. **最近发生时间**：当前选择时间范围内该簇最新故障发生时间或来源发布时间。
8. **典型证据**：该簇可用截图、日志和附件数量或受控入口摘要，不能直接泄露附件正文。
9. **涉及区域**：只统计来源记录中确实存在的省份或质量平台维修区域；无区域事实时明确显示“暂无区域数据”，不根据文本或 IP 猜测，也不恢复已删除的“省份热度排名”独立板块或下钻。
10. **操作**：查看簇详情，展示簇内反馈记录和归簇依据。

明确删除：影响版本。当前各渠道版本提取口径不稳定，不在一期问题簇列表展示或统计。

明确删除：渠道数、渠道字段。底层仍须保留每条反馈的来源渠道，以支持全渠道归簇、追溯和纠错，但一期明细列表不展示渠道统计。

不设置“近期反馈量”字段。当前时间范围内的反馈记录数配合首次发生时间、最近发生时间，已经能够表达规模与活跃情况；不得再增加固定 7 天等额外时间窗口，以免与用户选择的分析区间形成双重口径。

指标口径要求：用户数、设备数和反馈数必须由权限受控的程序查询计算；用户身份未知与 0 必须区分；设备数量固定按可用 `DEVICE_SN` 指纹计数，无 SN 时为 0；同一来源重复导入或双写重试不得重复计数。

问题簇详情的反馈记录字段包括完整问题内容、来源、关键信息、分析证据、故障时间或发布时间、归簇方式和详情操作。详情不展示严重度；关键信息及截图、日志、视频必须像四渠道列表一样提供直接查看入口，不再弹出用途/理由填写。技术角色查看原文，产品角色查看局部隐藏原文；附件仍须实时鉴权、安全状态校验、审计和 `no-store`，关闭弹窗或离开页面后清除敏感值与临时 Blob URL。产品角色日志只查看、不下载；ADMIN/RAW 技术角色可经独立固定用途令牌下载未截断原件。压缩日志的页面预览仍由服务端解压为有界文本，大文件必须明确提示截断，不能整包展开后阻塞页面，也不能用压缩包大小伪造解压文本的下载百分比。操作文案统一为“详情”，不得因列宽显示省略号。

### 5.3 跨渠道问题簇明细

- 在“全部去重问题簇明细”之后独立展示“跨渠道问题簇明细”。
- 每行问题簇在当前所选时间范围内必须至少命中学习机反馈、Jira、质量平台、红黑榜中的两个渠道；不能把单渠道簇放入该列表。
- 字段及指标口径与第 5.2 节一致，不恢复已删除的渠道数、渠道字段或“近期反馈量”。
- 两个明细列表独立分页；任一列表翻页不得重置或串改另一个列表的页码。

## 6. 归簇链路

- 一期删除隐私人工复核功能及其归簇前置门禁：不再生成需要人工判定或人工放行的隐私复核任务，既有 `REVIEW_NEEDED` 状态不得继续作为普通正文进入平台、搜索、索引、AI 或归簇的必要人工审批条件。
- 所有正文先执行现有脱敏规则；规则识别到的敏感值在写入普通内容前完成替换/遮蔽，脱敏成功后自动形成可用安全正文并直接进入平台、搜索、索引和问题簇归类，不等待人工复核。
- 所有成功完成规则脱敏的数据都必须参加问题簇归类，不得再因隐私复核状态、AI 分类结果或 AI 分类人工复核状态被遗漏。
- 历史处于 `REVIEW_NEEDED` 的记录须使用当前脱敏规则重新处理；成功后自动进入平台和归簇，不能要求人工逐条放行，也不能直接把未脱敏历史原文放行。
- 脱敏规则执行异常、密钥/存储错误或无法生成安全正文属于技术失败：必须失败关闭、记录可审计错误并自动重试或进入技术运维队列；不得泄露原文，也不得以“无需复核”为由绕过脱敏。技术故障恢复且脱敏成功后，数据必须补入归簇。
- AI 分类结果不得决定一条反馈能否进入归簇；分类服务异常也不得阻断归簇。
- 归簇 AI 仅处理已脱敏安全正文，并直接参与自动归簇决策：程序负责画像提取及全文、向量、错误签名和结构化候选召回，模型在完整召回候选集合内判断“关联已有簇或创建新簇”、选择目标簇并规范问题现象。程序必须校验目标属于候选集合、证据引用、硬冲突和置信阈值，通过后自动落库，不设置常规人工复核门禁；模型低置信、结构未知、调用失败或安全校验失败时回退确定性链路，原本需要人工确认的模糊边界默认保守新建簇，不能阻断反馈进入分析。统计数字、权限、脱敏和候选范围仍由程序控制。每次 AI 决策必须带模型、Prompt、输入事实摘要、输出、token、延迟和供应商请求号快照。
- 业务系统统一使用平台专属、可轮换和可审计的 OpenAI 项目 API Key，经环境变量或目标环境密钥托管注入；不得读取、导出或复用 Codex 登录凭据，不得把 Key 写入仓库、配置文件、日志或验收证据。活动模型必须由部署配置显式固定并通过对应评测，不在源码中隐式跟随“最新模型”。
- 原大模型供应商退出活动调用路由和生产门禁；历史 Prompt、模型版本、调用快照、评测和人工纠错事实继续保留用于审计与回滚，不物理改写历史记录。
- 本次变更删除的是人工隐私复核；一期关键信息和分析证据改为按技术/产品角色直接查看，不再使用用途申请式受控查验。规则脱敏、附件隔离/扫描、角色权限、审计和 `no-store` 仍保留；原始敏感值仍不得进入搜索、向量索引、AI、报表、导出或归簇分析。
- 后续优化重点是归簇准确性，包括跨渠道召回、双写去重、簇拆分/合并、人工纠错和可解释归簇依据。

## 7. 权限、登录与管理员

- 一期只允许通过 **飞书帐号** 登录的特定授权用户访问。
- 只向这些用户分配“渠道数据查看 + 问题深度分析”两个模块的打包权限；未获授权的飞书用户默认无这两个模块权限。
- 用户首次飞书登录后，平台创建或更新与飞书稳定身份绑定的账号；管理员页面以飞书姓名为主要展示名称，并明确标识飞书账号。
- 一期日常授权使用“用户与权限”页面：唯一管理员从已登录绑定的账号列表中选择用户，直接分配 `PHASE_ONE_TECHNICAL`（技术）或 `PHASE_ONE_PRODUCT`（产品）并保存。管理员无需手工填写 `open_id`、创建映射草稿或执行组织同步；后端必须通过所选平台账号校验其 SSO 类型和飞书稳定身份绑定，姓名只用于展示和搜索，不作为授权主键。
- 两个一期角色都必须独占，不能彼此组合，也不能与管理员、运营、审计或普通用户角色组合。二者共享一期工作区权限；只有技术角色额外持有原文权限，产品角色只能获得局部隐藏后的原文。权限包不允许在通用角色矩阵中修改。角色变更须立即使旧会话失效并记录变更前后角色、操作者和目标账号审计。
- 历史 `PHASE_ONE_USER` 账号升级时默认迁移为 `PHASE_ONE_PRODUCT`，避免在未确认人员类别前扩大原文权限；管理员再按实际职责改为技术角色。
- 当前只保留 **杨紫琦帐号** 为管理员。管理员匹配必须使用已绑定的飞书稳定用户 ID，不以姓名作为授权主键。
- 本地密码登录如因应急安全机制必须保留，也不得默认获得一期业务模块权限；是否彻底关闭入口需在实现时结合运维恢复方案确认。
- 权限调整和管理员变更必须留审计，不在文档中记录密码、Token、手机号或其他秘密。
