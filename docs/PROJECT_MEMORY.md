## 6. 高频踩坑与已验证处理方式

| 症状/误区 | 根因或正确判断 | 以后直接采用的处理方式 |
|---|---|---|
| 把“42”用于所有数量 | 42 是物理业务表；告警治理目录当前是 57 | 每个数字必须带量纲，禁止只写“当前共 42 个” |
| 把目录规则当成活动告警 | 目录、运行时版本和告警实例是三层对象 | 分别报告目录完整率、运行激活数、开放实例数 |
| Flyway checksum 漂移 | 编辑了已执行迁移或代码/数据库版本不匹配 | 恢复历史文件，新增前向迁移；有业务数据时先备份并查差异 |
| 一次性导入器启动后误连默认库或触发后台同步 | 安全启动脚本默认URL不等于launchd部署库；`spring.task.scheduling.enabled=false`不会关闭显式`@EnableScheduling` | 一次性任务必须显式传目标JDBC URL、关闭Flyway，并通过`app.scheduling.enabled=false`条件化禁用全部调度器；执行前后按渠道计数 |
| Flyway 文件变成三行 LFS 指针 | 全局 `*.sql` 被错误纳入 Git LFS，未拉取对象的环境无法执行迁移 | 源码型 SQL 使用普通 Git 文本；仅大型备份/产物 SQL 使用 LFS；提交前检查迁移目录不存在 LFS 指针 |
| 本地降级测试被写成生产通过 | LLM、Milvus、邮件、飞书等未配置时核心链仍可降级运行 | 明确写 `BLOCKED_EXTERNAL`/“待目标环境补验”，不得写 PASS |

## 7. 未完成、外部阻塞与优化队列

### 2026-08-20 明日计划：五渠道反馈页面优化

目标：基于五个渠道的真实数据重构列表、详情与操作区，让处理人员能快速定位问题，同时避免向产品等非诊断角色暴露不必要的敏感信息。五个渠道必须分别设计，禁止为了界面统一而展示渠道不存在或长期为空的字段。

1. **先审计真实数据，再定页面字段**：逐一核验 SDK、旧反馈平台、Jira、质量平台、红黑榜的源字段、有效覆盖率、数据质量和业务含义，形成“渠道 × 字段 × 覆盖率 × 展示角色 × 敏感级别 × 定位价值”矩阵。只展示该渠道真实拥有且能辅助定位的信息；不适用字段不渲染，不以空列或占位符制造无效信息。
2. **建立快速定位问题的核心字段体系**：按渠道适用性优先显示用户ID、故障发生时间、手机号、设备序列号、日志/日志拉取入口、功能模块、反馈状态，以及版本、机型、应用、网络、地域、来源链接等实际存在的辅助信息。列表展示高频定位字段，详情承载完整诊断上下文；“反馈时间”不再作为误导性核心字段，优先提取并展示真实故障发生时间。功能模块在AI分类完成并满足受控规则后确定，未确定时明确显示待分类，不伪造结果。
3. **各渠道单独选字段**：SDK/API渠道重点使用用户、设备、版本、故障时间、请求/错误上下文、应用日志，并提供受控日志拉取链接；Jira结合真实Issue字段、状态、人员、版本、描述维度和可用日志证据；旧反馈平台使用其真实用户、设备、产品、故障与附件/日志信息；质量平台保留商返单号、产品名称、产品型号、机身号码、派单/激活时间、区域、故障现象等定位信息；红黑榜保留UID、作者、来源平台、发布时间、情感/榜单类型、正文与原文链接等有效信息。来源记录ID、产品ID等无法理解的内部数字默认不在业务页面展示，但底层事实和审计关联不得删除。
4. **以“分发”替代“认领”**：移除主动认领语义，将权限控制的分发操作放入页面操作区。仅具有特定权限的人员可选择接收人/处理组进行分发；记录分发人、接收人、时间、原因、前后负责人和操作审计，支持必要的转派、接收确认与处理流转。复制不再作为主要页面操作，仅在确有使用价值的位置保留。
5. **在分发流程中增加提醒并支持失败回滚**：分发先进入通知中；站内通知任务、负责人变更、处理状态、分发状态和审计在同一事务中成立，通知任务写入失败时整笔分发回滚。异步实际投递最终失败时按幂等键执行补偿事务，恢复原负责人和原处理状态、将分发状态记为已回滚并保留失败/补偿审计；超时必须先查询供应商最终回执，补偿失败进入重试和告警。批量分发任一通知最终失败时整批补偿，避免部分成立。
6. **统一处理状态并保留来源事实**：页面只保留“处理状态”和独立的“分发状态”。各渠道原始状态通过版本化规则映射为新建、已分发、处理中、挂起、已解决、已关闭等统一处理状态；原始值、来源更新时间、映射版本、映射时间和结果继续作为不可覆盖底层事实及审计证据保存，但不再作为普通页面的独立状态字段，也不得被平台回写。人工处理结论优先，来源状态自动映射不得覆盖已进入人工处置的状态。

## 8. 低 Token 协作规则

- 默认只读取 `PROJECT_SNAPSHOT.md` 和当前任务表中的一个链接；仅在短快照不足时定向查询本文件，禁止开局通读本文件或 `archive/implementation/day*`。

- 2026-08-24最近7天只读审计基线：缓存命中率95.78%，但超过100k/200k的调用分别占56.60%/14.09%；最近一天主耗费任务157次调用、输入约1899万、最大上下文220k且仅压缩1次。缓存有效，主要问题是任务过长且没有按12次工具调用、60k软阈值和100k硬交接执行压缩。审计器现按时间窗统计活跃文件、按会话去重供应商并列出高耗费会话，不读取或输出会话正文。
