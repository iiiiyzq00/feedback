# 后端代码质量

## 工作方式

直接检查并完成用户要求的代码改动，不设置固定的长文档阅读、方案审批或停等门禁。仅在需求会产生明显不兼容、数据风险或不可逆影响时向用户确认。

修改前读取目标文件、直接调用方、直接依赖和相关测试。保留用户已有改动，不借机清理无关模块。修改后进行一次作者自审，并运行与风险相称的编译、静态检查或定向测试。

## 每次改动的硬性检查

### 中文注释

- 为公共类型、核心接口和复杂业务类补充中文职责说明，写清边界与不负责的事项。
- 对业务不变量、状态流转、幂等、并发、事务、失败关闭、安全规则和反直觉取舍使用中文注释。
- 注释解释“为什么”和约束来源，不逐行翻译代码，不写空泛的“处理数据”“调用服务”。
- 代码变更导致注释失真时同步更新或删除旧注释。
- 优先通过命名、短函数和明确类型表达意图；注释不能掩盖坏结构。

### 接口与类型

- 在跨层边界、存在多实现、需要隔离外部系统或需要独立测试替身时定义接口。
- 不为每个类机械创建一对一接口；没有替换价值的内部实现保持具体类型。
- HTTP/RPC 和稳定跨层契约使用明确的 Request、Response、Command、Query、DTO 或领域类型，避免 `Map<String, Any?>` 和持久化对象泄漏。
- 为公开字段写中文业务语义，并按需标明必填性、枚举、单位、时区、示例、权限和脱敏规则；请求参数使用可执行校验。

### 依赖与职责

- 每次触碰类时检查构造函数依赖是否都属于同一职责。
- 构造函数超过 5 个依赖时必须评估拆分；超过 7 个时原则上拆分用例、领域策略或外部能力门面，除非有清晰中文注释说明不能拆分的原因。
- 不通过 Service Locator、全局上下文、字段注入或把依赖塞进无语义容器来隐藏依赖数量。
- 优先按业务能力拆分，而不是按代码行数拆分；新抽象应降低耦合并可被单独测试。

### 事务

- 事务只包围需要原子性的数据库读写，避免把远程调用、文件操作、消息发送和重计算放在长事务中。
- 纯查询事务显式使用 `readOnly = true`；无需一致性快照的查询不滥用高隔离级别。
- 明确传播级别、隔离级别、锁顺序、重试、幂等和回滚语义；仅在偏离默认行为时配置。
- 警惕同类自调用导致 `@Transactional` 失效。需要独立事务时使用职责明确的协作者，而不是依赖代理偶然行为。
- 事务外副作用采用提交后事件、Outbox 或可补偿流程；不得出现“数据库已回滚但外部动作已发生”的静默不一致。
- 缩短事务前先冻结现有成功、失败和并发语义；若语义必须改变，补充测试并在交付说明中明确指出。

### 数据访问与错误处理

- 遵守项目既有 Mapper/Repository 分层；业务代码不新增直接 SQL，不制造 N+1 或无界批量查询。
- 不静默吞异常，不用无证据默认值掩盖数据或依赖故障。错误信息应可定位且不泄露敏感信息。
- 对重复请求、并发更新和部分失败给出确定行为；必要时使用唯一约束、乐观锁、幂等键或补偿机制。

## 完成标准

交付前逐项确认：

1. 改动范围内没有新增失真或低价值注释，关键约束已有中文说明。
2. 公共契约类型明确，接口抽象有真实边界价值。
3. 构造函数依赖数量与类职责相匹配，没有隐藏依赖。
4. 事务内没有非必要慢操作，原子性、回滚和并发语义有测试或清晰证据。
5. 正常、边界、失败及关键并发路径得到与风险相称的验证。
6. 最终说明列出代码质量改进、验证结果和仍未覆盖的风险，不把本机测试表述为生产验证。
